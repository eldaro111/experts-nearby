# Обновление: сжатие файлов и папок сборок

Добавлена загрузка папки целиком в разделе «Файлы проекта». При скачивании сайт восстанавливает обычный ZIP с исходными файлами и относительными путями. Отдельный файл сохраняется со сжатием только при экономии хотя бы 5%. Содержимое файлов не изменяется.

Скачивание подключено в рабочей зоне проекта, разделе «Файлы» и общем поиске. Старые файлы доступны по прежней схеме. В интерфейсе видны исходный размер и размер в хранилище, ход обработки и кнопка отмены подготовки/скачивания.

## Порядок установки архива обновления

Архив содержит изменённые файлы, а не отдельную копию всего сайта. Распаковывайте его **в существующий проект рядом с `package.json`**, заменяя совпадающие файлы. Docker не нужен. Новые API-ключи и отдельный сервер сжатия не требуются. Сжатие и восстановление выполняются в браузере пользователя; хранение остаётся в Supabase.

### 1. Подтянуть актуальный main

В **PowerShell**:

```powershell
cd "C:\Users\NucklearSnake\Desktop\Experts\experts-nearby-root\experts-nearby"
git status
```

Если есть свои незакоммиченные правки, сначала сохраните их отдельным коммитом. При чистом рабочем дереве:

```powershell
git fetch origin
git switch main
git pull --ff-only origin main
```

Теперь распакуйте архив обновления в эту папку. В ней должны появиться `UPDATE_FILE_COMPRESSION.md`, `src/lib/projectStorage` и новая SQL-миграция. Существующий `.env.local` сохраняется: его нет в архиве.

### 2. Проверить на тестовой базе и локально

В staging с актуальной схемой main откройте SQL Editor и выполните **весь SQL из файла** `supabase/migrations/20261101090000_project_file_compression.sql`. В SQL Editor нельзя вставлять команду PowerShell `Get-Content` — нужен текст, начинающийся с комментария и `begin;`.

В `.env.local` используйте существующие публичные URL и anon-ключ тестового Supabase. URL и ключ должны принадлежать одному проекту. Затем в PowerShell:

```powershell
npm ci
npm run check
npm run test:storage
npm run test:storage:bundle
npm run dev
```

Выполните проверки из следующего раздела. Если любая команда завершилась ошибкой, не переходите к публикации. `test:storage` использует временную локальную БД PGlite и не обращается к основной базе. Ему не нужны `service_role`, пароль PostgreSQL или Docker.

Если staging сейчас не соответствует main, сначала синхронизируйте его схему обычными миграциями проекта. Не выполняйте перенос или очистку основной базы ради этого обновления. Вместо локального запуска можно проверить отдельную ветку через Vercel Preview с настройками тестового Supabase.

### 3. Обновить основную базу

После проверки откройте **основной** Supabase `Experts-nearby` (`xvhntjcsolctjnzwuqjh`) и выполните ту же миграцию в SQL Editor. Она добавляет поля и обновляет функции загрузки, не удаляя и не переписывая существующие файлы/проекты/аккаунты. Повторный запуск проверен локально.

Правильный порядок: сначала SQL, затем отправка кода в main. До появления нового интерфейса текущая версия сайта продолжит работать с обычными файлами.

### 4. Отправить проверенный код в GitHub

В PowerShell, из той же папки проекта:

```powershell
git branch --show-current
git add -- .gitignore README.md UPDATE_FILE_COMPRESSION.md docs/FILE_COMPRESSION.md package.json package-lock.json public/vendor/THIRD_PARTY_NOTICES.txt
git add -- scripts/prepare-file-codecs.mjs scripts/tests/project-pack.test.ts scripts/tests/project-storage-db.mjs scripts/tests/project-worker-build.mjs src/lib/projectStorage
git add -- src/app/files/page.tsx src/app/search/page.tsx src/components/project/ProjectFiles.tsx src/components/project/types.ts supabase/migrations/20261101090000_project_file_compression.sql
git diff --cached --stat
```

Текущая ветка должна быть `main`. В списке — 20 файлов обновления, без `.env.local`, резервных копий базы, CAD-материалов и `node_modules`. После проверки списка:

```powershell
git commit -m "Add lossless project file and assembly compression"
git push origin main
```

Если `push` отклонён из-за новых коммитов в main, не используйте `--force`: сначала нужно получить и согласовать новые изменения. Эти команды используют вашу обычную авторизацию GitHub на компьютере; создавать новую репу или импортировать bundle не требуется.

### 5. Проверить публикацию

Vercel должен собрать **новый коммит main** с Production-переменными основной базы. Повторная сборка старого deployment не публикует новый код. Сверьте SHA в журнале Vercel с `git log -1 --oneline`. URL и anon-ключ Production должны остаться от основной базы, а не от staging. После успешной сборки повторите загрузку и скачивание на `nearbyexperts.ru`.

## Что проверить перед публикацией

1. Скачайте старый файл из существующего проекта: он должен открываться как раньше.
2. Загрузите небольшой текстовый файл с включённым сжатием. Скачайте и сравните SHA-256 исходного и полученного файлов: `Get-FileHash "полный-путь-к-файлу" -Algorithm SHA256`.
3. Выберите папку сборки с кириллицей в названиях и вложенными папками. Скачайте результат, распакуйте ZIP и откройте сборку в CAD-программе. Для совпадения ссылок на детали выбирайте общий корневой каталог со всеми зависимостями.
4. Скачайте эту же сборку через раздел «Файлы» и общий поиск. Во всех трёх местах должен получаться обычный ZIP, а не служебный контейнер.
5. Загрузите обычный ZIP как **отдельный файл**. При скачивании его байты должны совпасть с исходным ZIP. Сайт не распаковывает такие вложения при загрузке.
6. Попробуйте отмену подготовки и скачивания. Во время самой отправки в Storage отмена не предлагается: используется прежний механизм загрузки и резервации.
7. Участник проекта должен скачать файл; посторонний пользователь не должен получить к нему доступ. Удалите один новый тестовый файл и убедитесь, что остальные остались доступны.

## Лимиты хранилища

Лимит приложения: **500 МиБ исходных данных и 2000 файлов** в одной загрузке. Готовый контейнер тоже должен укладываться в 500 МиБ. Реальный допустимый размер объекта может быть меньше из-за настроек/тарифа Supabase. По документации Supabase на дату подготовки обновления Free ограничен 50 MB на объект. Наша тестовая сборка после сжатия занимает 71,81 MB и в такой лимит не помещается — для проверки на Free выберите меньшую папку.

Проверьте Global file size limit и ограничения бакета `project-files`. Бакет должен оставаться приватным. Если настроен список разрешённых MIME, для контейнеров нужен `application/vnd.nearby.project-pack`. Миграция не меняет тариф, не увеличивает лимиты и не включает публичный доступ.

Ссылки на первоисточники: [лимиты Supabase](https://supabase.com/docs/guides/storage/uploads/file-limits), [обычная загрузка](https://supabase.com/docs/guides/storage/uploads/standard-uploads). В этой версии сохранена обычная отправка через SDK; для крупных файлов следующим этапом нужна возобновляемая загрузка TUS. Supabase рекомендует её для файлов больше 6 MB. При обрыве обычной отправки передача начинается заново.

## Результат и границы проверки

На предоставленной CAD-сборке проверены **128 файлов**: после восстановления все пути и байты файлов совпали.

| Вариант | Размер в байтах | Размер, MB (1 MB = 1 000 000 байт) |
| --- | ---: | ---: |
| Исходные файлы внутри архива | 86 503 390 | 86,50 |
| Предоставленный ZIP | 82 314 532 | 82,31 |
| Новый контейнер папки | 71 805 241 | 71,81 |

Экономия на этом примере — около **17% относительно исходных файлов** и **12,8% относительно предоставленного ZIP**. Это результат одного набора, а не обещание такой же экономии для каждого проекта. Тестовые CAD-материалы в репозиторий не включены.

Автоматические проверки охватывают восстановление данных, повреждённые контейнеры, ограничения распаковки, кириллицу, RLS, финализацию, повторный запуск миграции и совместимость со старыми файлами. Дополнительно собранный браузерный Worker и загрузка WASM проверены в эмуляции окружения через Node VM. Сборка проверяется с фиктивными публичными значениями Supabase; это не проверка подключения к настоящему серверу. Полный браузерный сценарий загрузки в реальный Supabase в среде разработки не выполнен — перед публикацией нужны шаги выше.

Повторы убираются **в пределах одной загруженной папки**. Общего хранилища блоков между версиями и разными проектами пока нет. Пустые папки, права файлов и символические ссылки браузерный выбор папки не переносит. Для их сохранения загрузите самостоятельно подготовленный архив как отдельный файл. На слабых устройствах большие сборки могут не поместиться в память браузера; размер готового Blob тоже занимает ресурсы. Автоматического преобразования старых файлов нет.

## Если нужно временно остановить новые сжатые загрузки

Оставьте новый код скачивания и миграцию. В SQL Editor можно отключить создание новых контейнеров:

```sql
create or replace function public.project_file_storage_version()
returns integer language sql stable set search_path = public, pg_temp
as $$ select 0 $$;
notify pgrst, 'reload schema';
```

После перезагрузки страницы останется загрузка обычного файла. Сервер также отклонит новые запросы на создание контейнеров. Уже загруженные пакеты продолжат скачиваться новым кодом; начатые ранее резервации могут завершиться. Для повторного включения замените `select 0` на `select 1`. Повторное применение всей миграции тоже включает функцию.

Не откатывайте интерфейс к версии без декодера после появления сжатых файлов: старый код выдаст служебный контейнер вместо исходного файла. Не удаляйте новые поля и объекты Storage. Формат и устройство реализации описаны в [docs/FILE_COMPRESSION.md](docs/FILE_COMPRESSION.md).
