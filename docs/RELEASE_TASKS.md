## AUTH-01 — репетиция PostgreSQL / Supabase Auth / Mailpit

**Принято в пределах локальной синтетической репетиции.** Владелец принял ограниченную локальную репетицию Storage с исключениями из её отчёта. Старт от локальной `infra/er007-current-release`, коммит `b3b2b8a856655c60cc48b9f9e8624cb4b2d89213`. Использовать закреплённые в комплекте PostgreSQL и Supabase Auth. Новые отдельные проект Compose и тома; отдельная цель восстановления. Только синтетические аккаунты и локальные секреты, SMTP только в Mailpit, опубликованные порты только localhost. Не подключать production или сохранённые копии прежних этапов. До 2 часов, суммарно до 8 ГБ RAM и 4 CPU; сначала и в ходе прогона проверять свободные ресурсы. Чужие процессы не останавливать.

Проверить через настоящий Auth HTTP и полученные локальные письма:

1. Регистрация → письмо → подтверждение почты.
2. Вход с правильным паролем; отказ с неправильным.
3. Обновление токена, выход и дальнейшее поведение refresh/access согласно фактическим настройкам. Не считать продолжение жизни уже выданного access-токена автоматическим провалом.
4. Сброс по письму → новый пароль работает, прежний отклоняется.
5. Копия и восстановление в отдельную цель: прежний UUID, вход восстановленного пользователя, наблюдаемое поведение сессий относительно заранее обозначенного ожидания.
6. Сравнить ожидаемый журнал Auth до копии, после восстановления и после перезапуска. Расхождения объяснять, не переписывать историю ради совпадения.

Для V01 отметить локальный язык темы, текста и кнопки в реально полученных письмах. Вход по одноразовой ссылке проверить отдельно, если он доступен в рамках стенда. Не подменять наблюдение утверждением об облачном шаблоне; прохождение Auth и качество перевода — разные результаты.

**Ограничения и выход.** PostgREST не запускать; прежний отказ автоматической проверки разрешений не обходить. Для Edge/portfolio только описать необходимый состав и недостающий транспорт: SQL/мок не доказывают пользовательский HTTP-сценарий. Не менять MAINTAIN и исторические миграции, не ослаблять проверки. Указать дополнительные зависимости и частичные результаты. В конце остановить собственные контейнеры, сохранить тома и исходные доказательства вне Git. Остальные сценарии запускать по мере реализации. ⚑ — нужен стенд или отдельный серверный тест; ручной прогон охватывает только доступное через интерфейс. Отсутствие стенда = не проверено. В V11 явно проверить и положительный переход: исполнитель принимает актуальные условия, затем начинает задачу.

**V01-1 · Письма подтверждения, восстановления и входа по ссылке** ⚑
- **Роль/состояние:** новый пользователь на стенде Auth; почта — в локальном Mailpit.
- **Действия:** зарегистрироваться → открыть письмо подтверждения → перейти по кнопке; затем запросить восстановление пароля → открыть письмо → перейти; вход по одноразовой ссылке — отдельно, если стенд позволяет.
- **Ожидаемый результат:** у каждого письма понятные русские тема, заголовок, текст и кнопка; переход ведёт в правильный сценарий; среда проверки зафиксирована (язык почтового клиента не учитывается).
- **Признак провала:** английский текст/тема, кнопка ведёт не в тот сценарий, письмо не приходит.

**V02-1 ★ · Выбор пояса: список и поиск**
- **Роль/состояние:** пользователь с доступом к форме с выбором пояса (профиль/проект — по ER-002).
- **Действия:** открыть поле пояса → пролистать список → ввести в поиск «+05:30» и «+05:45» → ввести название города/зоны → найти две разные IANA-зоны с одинаковым сегодняшним смещением.
- **Ожидаемый результат:** русские подписи, поиск работает, числовой порядок по UTC, без дубликатов одного идентификатора, дробные смещения доступны, обе IANA-зоны в списке, список не ограничен 24/39 позициями.
- **Признак провала:** дубли идентификаторов, нет дробных смещений, город «угадывается» по UTC вместо сохранения зоны.

**V02-2 · Сохранение зоны и старые значения**
- **Роль/состояние:** пользователь с уже сохранённой зоной.
- **Действия:** выбрать зону → сохранить → перезагрузить страницу → открыть форму снова; отдельно проверить запись, где сохранено старое значение.
- **Ожидаемый результат:** выбранная зона сохранена и показана после перезагрузки; старые сохранённые значения не испорчены и не переименованы.
- **Признак провала:** после перезагрузки значение сброшено или заменено; старая запись изменилась.

**V03-1 · «Носитель» и PDF к языковому сертификату** ⚑ (файловый сценарий — зависит от стенда Storage)
- **Роль/состояние:** пользователь с языковым сертификатом уровня C2.
- **Действия:** проверить подписи значений в форме и профиле → по пути добавления PDF именно к языковому сертификату: загрузить → сохранить → открыть после перезагрузки; проверить видимость по правилам доступа; проверить пометку о непроверенной подлинности.
- **Ожидаемый результат:** значение называется «Носитель», существующий C2 не превращён в «Носитель»; PDF открывается после перезагрузки, доступ только по правилам видимости, пометка о непроверенной подлинности сохраняется.
- **Признак провала:** переименование C2, PDF не открывается после перезагрузки, отдельная кнопка портфолио вместо рабочего сценария, пометка исчезла.

**V04-1 ★ · Дедлайн проекта: ввод и сохранение**
- **Роль/состояние:** пользователь с правом редактирования дедлайна проекта.
- **Действия:** ввести полную дату и время клавиатурой → сохранить → перезагрузить; повторить тем же значением через календарь; ввести незавершённое/недопустимое значение → попытаться сохранить.
- **Ожидаемый результат:** полное значение сохраняется и после перезагрузки отображается ожидаемое время; полностью введённый 0436 сам по себе не ошибка; явная полная очистка снимает срок, а частичная дата не сохраняется, причина видна пользователю; ранее сохранённые даты не испорчены.
- **Признак провала:** после перезагрузки исчез прежний срок после стирания только дня или минут, недопустимое значение сохранилось без объяснения, съехала дата у уже сохранённых записей.

**V05-1 ★ · Остальные поля с датами: обход и граничные случаи**
- **Роль/состояние:** пользователь с доступом к проектам, задачам, событиям, спринтам.
- **Действия:** найти все остальные поля с датами/дедлайнами → применить к ним правила V04 (сводный список форм — в отчёт); в найденных формах проверить: пустое необязательное поле; конец раньше начала; поля в разных зонах; событие в 00:30. Для отсутствующего поля «только дата» отметить «не применимо».
- **Ожидаемый результат:** список проверенных форм возвращён; пустое необязательное допустимо, «конец раньше начала» отклоняется с видимой причиной, дата без времени не сдвигается на сутки.
- **Признак провала:** форма пропущена без записи; граничный случай сохраняет мусор; сдвиг суток у даты без времени.

**V06-1 · Планирование: русские подписи и словарь**
- **Роль/состояние:** пользователь, впервые открывающий настройки планирования.
- **Действия:** открыть настройки → проверить подписи и пояснения при первом употреблении (Kanban, Scrum, WIP, Product Owner, Scrum Master, Definition of Done, бэклог, спринт) → открыть словарь внизу страницы → сравнить описание с реальным поведением системы.
- **Ожидаемый результат:** русские подписи/пояснения при первом употреблении, словарь внизу; объяснено реальное поведение (например, мягкое ограничение отличается от строгого), а не только расшифровка аббревиатур.
- **Признак провала:** только английские термины без пояснений, словаря нет, описание расходится с фактическим поведением.

**V07-1 · Меню «Университеты и стартапы»**
- **Роль/состояние:** обычный пользователь; проверка на десктопе и мобильном.
- **Действия:** открыть меню → перейти в «Университеты», «Колледжи», «Стартапы» → повторить переходы с клавиатуры (Tab/Enter) и на мобильном.
- **Ожидаемый результат:** каждый пункт открывает соответствующий раздел или рабочий фильтр; доступен с клавиатуры и на мобильном; если у колледжей нет модели/данных — обозначена отдельная зависимость вместо пустой ссылки.
- **Признак провала:** пустая ссылка, пункт не доступен с клавиатуры, фильтр не соответствует названию.

**V08-1 · Демо: Томский политехнический университет** (только демо)
- **Роль/состояние:** обычный пользователь.
- **Действия:** открыть раздел вузов → найти ТПУ → сравнить структуру с официальным источником → проверить фильтрацию по вузу и подразделению.
- **Ожидаемый результат:** ТПУ добавлен как тестовый пример, структура соответствует официальному источнику, синтетические группы явно помечены, фильтрация работает; нет заявлений о партнёрстве и списков людей.
- **Признак провала:** фильтрация по вузу/подразделению не работает, структура не совпадает с источником, нет пометки о синтетичности.

**V09-1 · Общий календарь: создание события из дня**
- **Роль/состояние:** пользователь с правом создания событий хотя бы в одном проекте.
- **Действия:** нажать на день; отдельно повторить с клавиатуры (Enter) → убедиться, что дата предвыбрана → выбрать доступный проект → сохранить → перезагрузить.
- **Ожидаемый результат:** нажатие или Enter на дне открывает создание разрешённого события с предвыбранной датой; после сохранения событие видно в нужном дне после перезагрузки; при отсутствии прав — понятное состояние.
- **Признак провала:** дата не предвыбрана, событие не видно после перезагрузки, непонятный отказ при отсутствии прав.

**V10-1 ★ · Карточка «От первого отклика до готового решения»: название проекта**
- **Роль/состояние:** пользователь с одним доступным проектом и без проектов (два состояния).
- **Действия:** открыть карточку → нажать на название проекта; повторить, когда проекта нет или доступ утрачен.
- **Ожидаемый результат:** название открывает именно тот правильный доступный проект; при отсутствии проекта или утрате доступа нет ложной ссылки и чужих данных.
- **Признак провала:** ссылка ведёт не на тот проект, открываются чужие данные, «висячая» ссылка при утрате доступа.

**V10-2 ★ · Карточка: кнопка рабочего центра**
- **Роль/состояние:** пользователь с доступным проектом.
- **Действия:** нажать кнопку рабочего центра мышью → вернуться → повторить с клавиатуры (Tab/Enter).
- **Ожидаемый результат:** кнопка открывает рабочий центр, переход работает мышью и с клавиатуры.
- **Признак провала:** кнопка не реагирует, с клавиатуры недоступна, ведёт не в рабочий центр.

**V11-1 · Задача со штрафом: условия видны исполнителю**
- **Роль/состояние:** исполнитель, которому назначена задача со штрафом.
- **Действия:** открыть задачу → найти сумму/валюту или однозначную формулу, основания и порядок оспаривания.
- **Ожидаемый результат:** исполнитель видит сумму/валюту (или однозначную формулу), основания и порядок оспаривания до любого принятия.
- **Признак провала:** условия скрыты, формула двусмысленна, оспаривание не описано.

**V11-2 · Старт задачи заблокирован до принятия условий** ⚑ сервер
- **Роль/состояние:** исполнитель, не принявший условия; версия условий зафиксирована.
- **Действия:** попытаться начать задачу кнопкой → попытаться через доску → попробовать другой поддерживаемый путь запуска; зафиксировать исполнителя, версию условий и момент принятия.
- **Ожидаемый результат:** сервер не разрешает начать ни одним путём до явного принятия; фиксируются исполнитель, версия условий и момент принятия; согласование, предъявление и оплата различаются; автосписания нет.
- **Признак провала:** хотя бы один путь обходит барьер, принятие не зафиксировано, смешение согласования/предъявления/оплаты.

**V11-3 · Смена суммы: новое принятие обязательно** ⚑ сервер
- **Роль/состояние:** исполнитель, уже принявший условия задачи со штрафом.
- **Действия:** инициатор изменяет существенные условия (сумму) → исполнитель открывает задачу.
- **Ожидаемый результат:** требуется новое принятие; прежнее решение сохраняется в истории; новые суммы не применяются задним числом; без нового принятия задачу начать нельзя.
- **Признак провала:** новая сумма разрешает старт без повторного принятия, новая сумма применена задним числом.

**V11-4 · Смена исполнителя: новое принятие обязательно** ⚑ сервер
- **Роль/состояние:** новый исполнитель назначен на задачу со штрафом, условия уже принимались прежним исполнителем.
- **Действия:** сменить исполнителя → новый исполнитель открывает задачу → пытается начать без принятия.
- **Ожидаемый результат:** новому исполнителю требуется собственное принятие; решение прежнего исполнителя сохраняется и ему не навязывается.
- **Признак провала:** новый исполнитель начинает задачу без принятия, прежнее принятие «переехало».

**V11-5 · Задача без штрафа: барьера нет** ⚑ сервер
- **Роль/состояние:** исполнитель обычной задачи без штрафа.
- **Действия:** открыть задачу → начать работу.
- **Ожидаемый результат:** барьера принятия нет, задача начинается штатно.
- **Признак провала:** обычная задача требует денежное принятие.

**V12-1 · Правило 18+: до регистрации и в условиях** ⚑ сервер
- **Роль/состояние:** новый пользователь; версия правил зафиксирована.
- **Действия:** открыть регистрацию → проверить явное правило до регистрации (не предустановлено) → зарегистрироваться → войти разными способами → до подтверждения попытаться выполнить рабочее действие → перелогиниться в рамках той же версии.
- **Ожидаемый результат:** правило явное и до регистрации, подтверждение не предустановлено; сервер проверяет принятие для всех способов входа; рабочие действия ограничены до подтверждения; версия и дата сохранены; в рамках той же версии повторно подтверждать не просят.
- **Признак провала:** предустановленная галочка, рабочие действия доступны до подтверждения, повторное подтверждение при каждом входе.

**V12-2 · Старый аккаунт до введения правила**
- **Роль/состояние:** существующий пользователь, зарегистрированный до появления правила 18+.
- **Действия:** войти под старым аккаунтом → попытаться выполнить рабочее действие → подтвердить правило → повторить действие → перелогиниться в рамках той же версии.
- **Ожидаемый результат:** старый аккаунт до подтверждения ограничен рабочими действиями (сервер, не только интерфейс); после подтверждения — только действия в пределах прежних прав; в рамках той же версии повторно не спрашивают; фиксируются версия и дата подтверждения.
- **Признак провала:** старый аккаунт работает без подтверждения, интерфейс блокирует, а сервер нет, подтверждение запрашивается заново при каждом входе.

**V12-3 · Вход по ссылке проверяется сервером** ⚑ сервер
- **Роль/состояние:** пользователь, зарегистрировавшийся, но не подтвердивший правило 18+; доступен вход по одноразовой ссылке.
- **Действия:** запросить вход по ссылке → перейти по письму → попытаться выполнить рабочее действие.
- **Ожидаемый результат:** сервер проверяет принятие правила и для входа по ссылке; рабочие действия до подтверждения ограничены.
- **Признак провала:** вход по ссылке обходит барьер правила.

| LEG-01 | Перед публичным запуском сверить модель сервиса с документами и фактическими процессами. Оператор и контакты, политика ПД, основания, сроки хранения и удаление по запросу, публичные профили, размещение данных, применимость уведомления РКН. При отсутствии таких сервисов зафиксировать результат проверки. Ответственный за прогон пока не назначен. Отдельно определить роль в расчётах, применимость оферты, возвратов, комиссий и лицензий/прав на материалы. Проверить согласованность с V11/V12. Указать, что обеспечивает платформа, что проверено локально, что остаётся неизвестным. Это не разрешение менять MAINTAIN, переносить реальные данные или проверять production. |

## Охват полной дорожной карты

Двенадцать замечаний Влада — один пакет. По числу V-карточек нельзя считать процент готовности релиза. Таблица связывает текущие поручения с [исходным ТЗ](../EXPERTS_ROADMAP_CODEX.md), [дорожной картой](ROADMAP.md) и [состоянием проекта](PROJECT_STATE.md); она не меняет назначения и не объявляет отложенным весь объём вне активной волны.

| Направление | Что учитывать при сборке и приёмке |
|---|---|
| ER-000, ER-001 | Инвентаризация и регрессия существующего приложения; навигация, подвал, старые ссылки, мобильные экраны. V07 и V10 покрывают только части навигации. |
| ER-002, ER-004 | Выбор зоны и фильтр; отдельно — рабочие дни, пересечение интервалов, полночь и сезонная смена времени. V02 не закрывает расписания. ## Передача результата и обновление

Формат ответа: **ID · ветка и SHA (если есть) · результат/доказательство и среда · что не проверено или блокирует · следующий шаг**. Если нет доступа к стенду, это «не проверено», а не FAIL; статическая проверка, мок и настоящий сервис указываются раздельно.

Координатор перед обновлением перечитывает последнюю версию из этой ветки. Принимает изменения по существующему ID; новый ID добавляет только для нового объёма. Состояния: «в очереди» → «назначено» → «на проверке» → «принято», либо «блокировано» с конкретной причиной. Для принятия нужны доказательства по критериям и явные исключения. Локальный коммит не означает публикацию. После первых отчётов: решить оставшиеся вопросы Auth; затем отдельно назначать реализацию V12, следующую группу интерфейса, файловый сценарий и V11. Очередь не запускается автоматически.
