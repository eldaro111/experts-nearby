## AUTH-01 — репетиция PostgreSQL / Supabase Auth / Mailpit

**Назначено Codex.** Владелец принял ограниченную локальную репетицию Storage с исключениями из её отчёта. Старт от локальной `infra/er007-current-release`, коммит `b3b2b8a856655c60cc48b9f9e8624cb4b2d89213`. Использовать закреплённые в комплекте PostgreSQL и Supabase Auth. Новые отдельные проект Compose и тома; отдельная цель восстановления. Только синтетические аккаунты и локальные секреты, SMTP только в Mailpit, опубликованные порты только localhost. Не подключать production или сохранённые копии прежних этапов. До 2 часов, суммарно до 8 ГБ RAM и 4 CPU; сначала и в ходе прогона проверять свободные ресурсы. Чужие процессы не останавливать.

Проверить через настоящий Auth HTTP и полученные локальные письма:

1. Регистрация → письмо → подтверждение почты.
2. Вход с правильным паролем; отказ с неправильным.
3. Обновление токена, выход и дальнейшее поведение refresh/access согласно фактическим настройкам. Не считать продолжение жизни уже выданного access-токена автоматическим провалом.
4. Сброс по письму → новый пароль работает, прежний отклоняется.
5. Копия и восстановление в отдельную цель: прежний UUID, вход восстановленного пользователя, наблюдаемое поведение сессий относительно заранее обозначенного ожидания.
6. Сравнить ожидаемый журнал Auth до копии, после восстановления и после перезапуска. Расхождения объяснять, не переписывать историю ради совпадения.

Для V01 отметить локальный язык темы, текста и кнопки в реально полученных письмах. Вход по одноразовой ссылке проверить отдельно, если он доступен в рамках стенда. Не подменять наблюдение утверждением об облачном шаблоне; прохождение Auth и качество перевода — разные результаты.

**Ограничения и выход.** PostgREST не запускать; прежний отказ автоматической проверки разрешений не обходить. Для Edge/portfolio только описать необходимый состав и недостающий транспорт: SQL/мок не доказывают пользовательский HTTP-сценарий. Не менять MAINTAIN и исторические миграции, не ослаблять проверки. Указать дополнительные зависимости и частичные результаты. В конце остановить собственные контейнеры, сохранить тома и исходные доказательства вне Git. В локальный коммит — только проверочный код и отчёт без секретов. По каждому пункту: PASS / FAIL / не проверено, основание, следующий конкретный шаг.

## Передача результата и обновление

Формат ответа: **ID · ветка и SHA (если есть) · результат/доказательство и среда · что не проверено или блокирует · следующий шаг**. Если нет доступа к стенду, это «не проверено», а не FAIL; статическая проверка, мок и настоящий сервис указываются раздельно.

Координатор перед обновлением перечитывает последнюю версию из этой ветки. Принимает изменения по существующему ID; новый ID добавляет только для нового объёма. Состояния: «в очереди» → «назначено» → «на проверке» → «принято», либо «блокировано» с конкретной причиной. Для принятия нужны доказательства по критериям и явные исключения. Локальный коммит не означает публикацию. После первых отчётов: решить оставшиеся вопросы Auth; затем отдельно назначать реализацию V01/V12, следующую группу интерфейса, файловый сценарий и V11. Очередь не запускается автоматически.
