# Развёртывание пилота на nearbyexperts.ru

Документ подготовлен 4 октября 2026. Это инструкция для владельца инфраструктуры; описанные операции с production и DNS ещё не выполнялись.

## Ответ техническому эксперту клиента

`*.vercel.app` — стандартный адрес размещённого на Vercel приложения. По нему нельзя определить, делало ли сайт агентство, штатная команда или разработчик с ИИ-инструментами. Исходный код этого проекта — Next.js/React; интерфейс обращается к Supabase.

Предлагаемая точка входа пилота — **https://nearbyexperts.ru**. Пользователь открывает сайт в браузере. В текущем коде API, авторизация, PostgreSQL и файлы обслуживаются **отдельным проектом Supabase**, адрес которого задаёт `NEXT_PUBLIC_SUPABASE_URL`. Загрузка PDF проходит через Supabase Edge Function `portfolio` (`/functions/v1/portfolio`). Привязка домена сайта к Vercel не переносит эти сервисы.

| Часть | Текущая схема кода | Что нужно согласовать |
| --- | --- | --- |
| Вход пользователя | nearbyexperts.ru → Next.js на выбранном хостинге | Привязка домена/HTTPS и основной адрес без www |
| API и Auth | URL проекта Supabase, REST/RPC/Auth | Регион хранения и допустимый контур обработки данных |
| Файлы | Закрытые бакеты Supabase Storage | Регион, резервирование, сроки хранения |
| PDF API | Supabase Edge Function `portfolio` | Развернуть после миграции и проверить на staging |
| api.nearbyexperts.ru | Пока не подключён и не используется | Если нужен единый брендированный API, отдельно настроить поддерживаемый custom domain или свой API-шлюз, Auth, TLS и WebSocket; одного CNAME недостаточно |
| Деньги/эскроу | Интеграции ещё нет | API, sandbox, подписанные события и договоры партнёра |

Два возможных контура: продолжить существующий Vercel + Supabase после проверки допустимости размещения, либо перенести приложение и совместимый backend в согласованный российский контур. Не объявлять первый вариант юридически готовым, пока неизвестны регион и основания обработки. Перенос требует проекта/сервера и доступа, это не изменение текста домена в коде.

## 2. Тестовая база и миграция

1. Сделать проверяемую резервную копию рабочей БД и конфигурации Storage/Auth. Для теста использовать отдельный Supabase-проект или восстановленную копию с обезличенными данными.
2. Убедиться, что таблицы соответствуют исходному baseline. Для **существующей** базы не запускать baseline повторно: он создаёт уже существующие объекты. Если база настраивалась вручную, сначала сопоставить миграционную историю и текущую схему.
3. На свежем тестовом проекте применять все миграции по времени; на существующей совместимой схеме — `supabase/migrations/20261004090000_pilot_feedback.sql`, затем `supabase/migrations/20261004150000_recommendations.sql`. Если первая уже установлена, применить только вторую. Каждая выполняется транзакцией, добавляет таблицы/поля, политики и RPC; повторно вручную миграции не запускать.
4. Проверить заполнение `expert_code` и ограничения новых полей. Не копировать `hourly_rate` в `price_from`: условия меняет сам эксперт.
5. Синхронизировать историю миграций штатным инструментом команды. При использовании Supabase CLI сначала `supabase db push --dry-run` на связанном **тестовом** проекте; проверить список. Не выполнять `db reset` на production.

Автотесты без внешней БД:

```bash
npm ci
npm run test:db
npm run test:recommendations
npm run typecheck
npm run lint
npx playwright install chromium
npm run test:ui
```

`test:db` поднимает изолированный PostgreSQL-движок PGlite в памяти, создаёт минимальные аналоги управляемых схем Supabase и применяет реальные SQL-миграции. Проверяет 43 сценария прав и правил. `test:recommendations` отдельно проверяет подбор, оповещения и приватность; порядок включения — в [RECOMMENDATIONS.md](RECOMMENDATIONS.md). Эти тесты не эмулируют весь PostgREST, Auth, Realtime, доставку email или Storage API.

## 3. Развернуть сервер загрузки портфолио

После миграции на целевом тестовом Supabase:

```bash
supabase login
supabase link --project-ref YOUR_TEST_PROJECT_REF
supabase functions deploy portfolio --project-ref YOUR_TEST_PROJECT_REF
```

В `supabase/config.toml` для `portfolio` указано `verify_jwt=false`: функция сама проверяет Bearer-токен через `auth.getUser()` перед доступом к данным. Это не анонимная загрузка. Такая проверка работает с текущим Auth и не зависит от проверки legacy JWT на gateway.

Функции нужны серверные переменные `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY` в среде Supabase. Service role не добавлять в Vercel `NEXT_PUBLIC_*`, исходники или ZIP. Бакет `portfolio` остаётся закрытым; прямых политик браузерной записи нет. Объект появляется в публично доступном портфолио только после успешной финализации и при разрешающей видимости профиля.

На staging проверить PDF <15 МиБ, превышение общей квоты, переименованный не-PDF, повторную загрузку, удаление, истёкший JWT, чтение чужого скрытого портфолио. Проверка сигнатуры не заменяет антивирус: если пилот требует сканирование файлов, добавить карантин/проверку до состояния `ready`.

## 4. Переменные приложения и редактор

Заполнить все нужные значения из `.env.example` в настройках окружения хостинга. `NEXT_PUBLIC_SITE_URL=https://nearbyexperts.ru`. `NEXT_PUBLIC_*` встраиваются при сборке: после изменения нужна новая сборка. Для preview задавать отдельный тестовый Supabase и адрес тестового сайта.

`NEXT_PUBLIC_LEGAL_NAME` — реальное полное/утверждённое название ООО; `NEXT_PUBLIC_LEGAL_DETAILS` — согласованные реквизиты. `NEXT_PUBLIC_CONTACT_EMAIL`, `NEXT_PUBLIC_VK_URL`, `NEXT_PUBLIC_TELEGRAM_URL` — реальные контакты. Пустые соцссылки не показываются. До заполнения реквизитов в © остаётся название платформы.

Редактор сначала регистрируется и заполняет профиль. Администратор БД однократно выдаёт права конкретному проверенному UUID:

```sql
insert into public.site_editors(user_id)
values ('UUID_OF_VERIFIED_EDITOR')
on conflict do nothing;
```

Открыть `/editor`, загрузить утверждённые тексты четырёх документов, указать версии и опубликовать. Заглушки не являются действующим пользовательским соглашением. Публикации о мероприятиях также нужно заполнить реальными материалами. Роли «Представитель вуза» в профиле недостаточно для прав редактора.

## 5. Домен и HTTPS на существующем Vercel

Этот вариант применим, если команда выбрала и согласовала существующий контур Vercel/Supabase.

1. В правильном Vercel-проекте открыть **Settings → Domains**, добавить `nearbyexperts.ru` и `www.nearbyexperts.ru`. Основным назначить адрес без `www`, второй перенаправить на него.
2. Сохранить текущие DNS-записи у регистратора. Внести для корня и `www` **те A/CNAME/TXT значения, которые Vercel показывает именно для этого проекта**. Здесь намеренно нет универсального IP: он может отличаться. Смена всех NS не обязательна; при точечной правке A/CNAME почтовые MX/TXT и прочие записи остаются на месте.
3. Дождаться статуса корректной конфигурации и выпуска HTTPS. Проверить основной адрес, `www` и HTTP → HTTPS. Настроить перенаправление прежнего production-адреса, если оно необходимо; preview-адреса оставить для теста.
4. Production должен собираться только после применения совместимой миграции и функции. Проверить env, `npm ci`, `npm run build`. Не делать автоматический deploy этого релиза на старую схему БД.
5. В Supabase **Authentication → URL Configuration** установить Site URL `https://nearbyexperts.ru`; разрешить точные используемые callback-адреса:
   - `https://nearbyexperts.ru/auth/callback?type=signup`
   - `https://nearbyexperts.ru/auth/callback?type=magiclink`
   - `https://nearbyexperts.ru/auth/callback?type=recovery`
   - `https://nearbyexperts.ru/auth/callback` — если используется без параметров.
   Для staging держать отдельный список адресов. Не разрешать произвольные внешние домены.
6. Проверить шаблоны Supabase email и их использование RedirectTo, если шаблоны менялись. Настроить рабочую отправку писем и DNS почты (SPF/DKIM/DMARC по данным SMTP-провайдера), проверить доставку регистрации, входа и восстановления.
7. Повторить сценарии ниже на настоящем HTTPS-домене. Добавить мониторинг доступности, ошибок Auth/Edge Function и резервного копирования; назначить ответственного.

## 6. Приёмка пилота

- Гость видит публичные страницы и утверждённые документы; скрытые данные недоступны прямыми запросами API.
- Новая регистрация требует совпадения паролей, email-письмо возвращает на nearbyexperts.ru, восстановление работает.
- Студент сохраняет вуз/школу/группу; соответствующие фильтры находят его и проекты. Переключение вуза очищает зависимые фильтры.
- У эксперта есть код ER, условия в рублях, опыт и языки; сертификат не обозначается проверенным автоматически.
- Обращение приходит правильному эксперту, повторное запрещено; посторонний не читает и не отвечает. После согласия создаётся один проект с приглашением.
- PDF проходят серверные проверки, суммарная квота соблюдается; скрытое портфолио недоступно другим.
- До завершения проекта отзыв запрещён и через интерфейс, и через API. После завершения команда/задачи фиксированы, отзыв доступен участникам.
- Обычный пользователь не публикует новости/документы и не назначает себя редактором.
- Рабочие прежние сценарии — аукционы, чат, календарь, проектные файлы — проходят существующую staging-проверку из `README_TZ05_STAGING.md`.

## Откат

Перед релизом сохранить прежний build и backup БД/Storage. Новая миграция добавляет поля, но меняет правила отзывов и выдачу кодов; возврат старого frontend не отменяет эти правила. При проблеме сначала ограничить доступ к изменённым сценариям, сохранить данные/логи, исправить совместимость. Не удалять новые таблицы с данными ради визуального отката. Восстановление БД из backup требует отдельного согласованного окна и учёта данных, появившихся после backup.
