## Решения до реализации

Прочитан целиком `experts-nearby-claude/docs/reports/planning-modes-contract.md` (пакет `claude/ui-motion-planning`, интерфейс `4d4f4f8`, проектирование `e274418`). Это предложение, а следующий контракт уточняет его для существующей схемы.

1. Единственный признак завершения — существующий `tasks.status = 'done'`. Этап категории `done` имеет только эффективный статус `done`; другие категории не могут выдавать `done`. Старые произвольные статусы сохраняются. Перемещение в этап устанавливает его статус; изменение статуса старым клиентом выбирает активный этап с **точно совпадающим** эффективным статусом либо оставляет `stage_id = NULL`. Нет подмены `review` произвольным первым этапом. Эффективные статусы активных этапов уникальны. `completed_at` устанавливается сервером при настоящем переходе в done, очищается при повторном открытии. Неизменённые старые строки и история не переписываются; прежний неизвестный момент завершения остаётся неизвестным.
2. Отсутствие `project_planning` означает simple / soft / делегирование выключено / версия 0. Оценки доступны во всех режимах. Simple не применяет WIP. Правила этапа и Definition of Done — поясняющий текст, не исполняемый SQL. Строгий WIP ограничивает входящие задачи; уменьшить лимит ниже текущего заполнения или включить strict при переполнении нельзя. Soft разрешает переход, состояние переполнения вычисляется по фактическому составу.
3. Настройками, этапами и спринтами управляет автор; явное включение делегирования даёт управление текущим Product Owner / Scrum Master. Назначение ролей и само делегирование остаются у автора. Проверяется действующее членство, не только запись роли. Исключение участника удаляет назначенные ему роли. Порядок бэклога меняют только автор и действующий Product Owner, независимо от делегирования. Оценки и этапы задач изменяют текущие участники, как задачи старого интерфейса.
4. Все новые таблицы приватны для участников; прямые INSERT/UPDATE/DELETE новых сущностей закрыты клиентским ролям. Для существующих задач сохраняется DML с прежним RLS, а триггеры проверяют этап, проект, оценки, WIP и пишут историю даже без RPC. Клиентам не открываются внутренние функции истории.
5. Новые RPC блокируют проект, затем связанные сущности; задачи блокируются в порядке UUID. Проект служит общей точкой сериализации, включая изменения членства и закрытие. Старый прямой DML уже держит строку задачи/заявки: его существующий guard получает проект через `NOWAIT` и сообщает конфликт `PT409`, если проект занят. Он не ждёт в обратном порядке. RPC сроков сохраняет сигнатуру, но получает проект перед задачей. Прямые запросы старого клиента без сравнения версии по-прежнему не гарантируют обнаружение последовательно потерянной правки; новый клиент обязан использовать версионный RPC.
6. Изменяющие RPC требуют ожидаемые версии. Сначала проверка версии, затем сравнение значений. Повтор setter с текущей версией и теми же значениями — no-op без события; повтор старта уже активного спринта с текущей версией также no-op. Повтор со старой версией после успешного изменения — **конфликт**, даже если полезная нагрузка совпадает. Закрытый спринт закрывать повторно нельзя: старая версия даёт PT409, текущая — 23514. Реестра request_id нет; сетевой таймаут требует перечитать состояние. Создание требует версию контейнера. Не обещается идемпотентность создания/закрытия по произвольному повтору.
7. Бэклог хранит порядок отдельно от `tasks`: это закрытая таблица, поэтому старый прямой UPDATE задачи не может обойти права на порядок. Клиент не пишет `backlog_rank` в задачу. Завершённые задачи и задачи в открытом составе спринта исключаются из текущего бэклога. Повторно открытая задача без открытого состава возвращается в бэклог; её прежний спринт не переписывается.
8. Планируемый состав спринта изменяют участники; состав активного — только управляющий планированием. Старт и закрытие — управляющий. Один активный спринт на проект. При выходе из scrum активный спринт нужно завершить/отменить. Завершение/отмена требуют решения для каждой незавершённой задачи: бэклог либо конкретный планируемый спринт того же проекта. Перенос сохраняет UUID задачи.
9. При старте сохраняется неизменяемый снимок состава/оценок. При закрытии — отдельный снимок итогов и удалённых/исключённых элементов. Идентификатор исходной задачи и снимки переживают удаление самой задачи; живой FK обнуляется. Последующие оценки, повторное открытие и удаление не меняют закрытые результаты. Story Points и часы хранятся и суммируются раздельно; NULL — не оценено, не ноль. Исторические события не создаются задним числом и не являются оценкой качества/труда человека.
10. Закрытый проект доступен для чтения; планирование и задачи в нём не меняются. Занятый этап нельзя переопределить с другой семантикой: нужен новый этап и явный атомарный перенос при архивировании. Нельзя привязать задачи/этапы/спринты разных проектов. Удаление проекта остаётся существующей отдельной операцией, каскадно удаляющей его данные; сохранение результатов относится к удалению **задач**, не к удалению всего проекта.

### Точный API этапа 2 для Клода

Названия ниже заменяют предлагаемые в исходном контракте; это новые API, опубликованный клиент их пока не вызывает. `p_expected_version` для спринта — `project_sprints.version`. Любое действительное изменение задачи в открытом составе, даже старым UPDATE, увеличивает версию спринта; перед стартом/закрытием и редактированием состава её нужно перечитать. Конфликт — основание показать актуальные данные, не автоматически перезаписать их.

| RPC | Параметры | Результат / правила |
| --- | --- | --- |
| `get_project_backlog` | `p_project_id uuid` | JSON `{project_id, version, tasks:[полные строки tasks]}`; текущий участник, включая чтение закрытого проекта |
| `reorder_project_backlog` | `p_project_id uuid, p_expected_version bigint, p_task_ids uuid[]` | Тот же JSON; **полный** порядок текущего бэклога, не более 5000 уникальных UUID; автор/действующий PO |
| `create_project_sprint` | `p_project_id uuid, p_expected_planning_version bigint, p_name text, p_goal text, p_start_at timestamptz, p_end_at timestamptz` | `project_sprints`; управляющий, scrum; увеличивает версию настроек проекта, сервер назначает номер |
| `update_project_sprint` | `p_sprint_id uuid, p_expected_version bigint, p_name text, p_goal text, p_start_at timestamptz, p_end_at timestamptz` | `project_sprints`; управляющий, planned/active, scrum; полные значения |
| `add_tasks_to_sprint` | `p_sprint_id uuid, p_expected_version bigint, p_tasks jsonb` | `project_sprints`; массив `[{"task_id":"UUID","expected_version":N}]`, максимум 5000; planned — участник, active — управляющий |
| `remove_task_from_sprint` | `p_sprint_id uuid, p_expected_version bigint, p_task_id uuid, p_expected_task_version bigint` | `project_sprints`; те же права; история прежнего включения остаётся, задача не удаляется |
| `start_project_sprint` | `p_sprint_id uuid, p_expected_version bigint` | `project_sprints`; управляющий, scrum, непустой planned с обеими датами; стартовый снимок |
| `close_project_sprint` | `p_sprint_id uuid, p_expected_version bigint, p_cancel boolean, p_reason text, p_decisions jsonb` | `project_sprints`; управляющий; complete только active, cancel planned/active; для cancel непустая причина до 2000 символов |

Пример `p_decisions` (синтетические заполнители, не готовая команда для основной базы):

```json
[
  {"task_id":"UUID_A","destination":"backlog"},
  {"task_id":"UUID_B","destination":"sprint","sprint_id":"UUID_PLANNED","expected_sprint_version":4}
]
```

Массив содержит **ровно** каждую текущую незавершённую задачу открытого состава, по одному разу. Для выполненных/удалённых/ранее исключённых задач решения не передаются. Цель переноса — planned того же проекта; проверяется её ожидаемая версия до любых изменений. Пустой массив допустим, когда незавершённых нет. Отмена планируемого спринта допускается после выхода из scrum, чтобы не запереть его задачи. Завершение не меняет статусы задач автоматически.

Бэклог хранится в `project_backlogs.task_order` с общей версией, без нового столбца `tasks.backlog_rank`. Новые/повторно открытые задачи, не перечисленные в порядке, добавляются при чтении по `(created_at,id)` после перечисленных. Завершённые и входящие в любой открытый состав отфильтрованы. Любая настоящая правка задачи и любое изменение состава увеличивает версию бэклога консервативно, даже если визуальный порядок не поменялся. Удалённые UUID в старом массиве не возвращаются читателю; следующая перестановка заменяет массив целиком. Серверная проверка полного множества исключает потерю новой задачи при устаревшем drag-and-drop.

Один активный спринт обеспечен и RPC, и уникальным частичным индексом. У задачи только одно открытое включение; повторное добавление после исключения создаёт новый **элемент истории состава**, а не новую задачу. Начало/конец planned могут быть NULL, но если обе даты указаны, конец строго позже начала; active требует обе даты. Плановые даты не являются автоматическим расписанием запуска. `started_at/closed_at` — фактические серверные отметки. Изменение плановых дат активного спринта не меняет стартовый снимок.

Прямое удаление задачи активного спринта проверяет те же права управляющего; planned-задачу может удалить обычный действующий участник по прежнему task RLS. При удалении сохраняются последний снимок и outcome `deleted`; FK `live_task_id` обнуляется, первоначальный `task_id` остаётся. `start_snapshot` и `final_snapshot` хранят независимые данные, а не ссылки для вычисления задним числом. Удаление задачи закрытого спринта меняет только живой FK, не итог/оценки/историю.

Для будущих графиков читать приватные `project_sprints`, `project_sprint_items`, `project_sprint_events`. У снимка поля `items`, `totals`, `completed`; суммы `story_points`/`planned_hours` независимы, рядом `unestimated_points`/`unestimated_hours`. Если оценённых элементов нет, сумма NULL; пустой список имеет `tasks=0`. В итоговых totals входят `done/backlog/moved`; исключённые/удалённые сохранены в items, но не складываются повторно. Метрики стартовых оценок нужно брать из start_snapshot, итоговых — из final_snapshot; это разные срезы, их нельзя незаметно заменять друг другом. Отменённые спринты не смешивать с выполненными при расчёте velocity. В `project_sprint_events` сохраняются изменения задачи до/после, в том числе повторное открытие, и изменения состава; порядок — `id`, пропуски sequence после отката допустимы. Это данные для будущих графиков, не реализованная аналитика ER-005 и не оценка человека.

Realtime для новых таблиц не включался: первый будущий клиент должен перечитывать RPC/SELECT после изменения и при PT409. `edit_task_planning` заменяет два предлагаемых отдельных RPC move/estimate и защищает их общей версией. Для статуса/сроков старого клиента используются прежние операции с триггерами. Внутренние функции остаются недоступны клиенту; типы новой истории имеют `entity_type='planning'`, UUID сущности и структурированные metadata. UI-форматтер для новых типов — будущая задача Клода.

### Блокировки и границы повторов

Все изменяющие новые RPC сначала блокируют единственный `listings` проекта; настройки/бэклог и исходный спринт блокируются после проекта. Архивирование берёт затронутые этапы по UUID; закрытие — исходный спринт, затем целевые спринты по UUID. Множественные задачи — по UUID, элементы состава/события — после них. Общая блокировка проекта сериализует эти разные порядки дочерних сущностей. У direct task/application DML строка уже заблокирована движком, поэтому guard берёт проект через NOWAIT, а не ожидает его в обратном порядке. Триггер задачи обновляет спринт только после успешного получения проекта. Проверены **READ COMMITTED** и указанные ниже чередования, не произвольные много-проектные SQL-транзакции/другие уровни изоляции.

Реестр запросов/request_id не реализован. Новая запись спринта защищена ожидаемой версией настроек; это предотвращает слепое повторное создание с той же версией, но не является общей идемпотентностью. При таймауте читать состояние и историю; не увеличивать expected_version автоматически. Точечный `PT409` от NOWAIT означает конфликт работы в проекте; повтор возможен после получения актуального состояния.
