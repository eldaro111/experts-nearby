## Решения до реализации

Прочитан целиком `experts-nearby-claude/docs/reports/planning-modes-contract.md` (пакет `claude/ui-motion-planning`, интерфейс `4d4f4f8`, проектирование `e274418`). Это предложение, а следующий контракт уточняет его для существующей схемы.

1. Единственный признак завершения — существующий `tasks.status = 'done'`. Этап категории `done` имеет только эффективный статус `done`; другие категории не могут выдавать `done`. Старые произвольные статусы сохраняются. Перемещение в этап устанавливает его статус; изменение статуса старым клиентом выбирает активный этап с **точно совпадающим** эффективным статусом либо оставляет `stage_id = NULL`. Нет подмены `review` произвольным первым этапом. Эффективные статусы активных этапов уникальны. `completed_at` устанавливается сервером при настоящем переходе в done, очищается при повторном открытии. Неизменённые старые строки и история не переписываются; прежний неизвестный момент завершения остаётся неизвестным.
2. Отсутствие `project_planning` означает simple / soft / делегирование выключено / версия 0. Оценки доступны во всех режимах. Simple не применяет WIP. Правила этапа и Definition of Done — поясняющий текст, не исполняемый SQL. Строгий WIP ограничивает входящие задачи; уменьшить лимит ниже текущего заполнения или включить strict при переполнении нельзя. Soft разрешает переход, состояние переполнения вычисляется по фактическому составу.
3. Настройками, этапами и спринтами управляет автор; явное включение делегирования даёт управление текущим Product Owner / Scrum Master. Назначение ролей и само делегирование остаются у автора. Проверяется действующее членство, не только запись роли. Исключение участника удаляет назначенные ему роли. Порядок бэклога меняют только автор и действующий Product Owner, независимо от делегирования. Оценки и этапы задач изменяют текущие участники, как задачи старого интерфейса.
4. Все новые таблицы приватны для участников; прямые INSERT/UPDATE/DELETE новых сущностей закрыты клиентским ролям. Для существующих задач сохраняется DML с прежним RLS, а триггеры проверяют этап, проект, оценки, WIP и пишут историю даже без RPC. Клиентам не открываются внутренние функции истории.
5. Новые RPC блокируют проект, затем связанные сущности; задачи блокируются в порядке UUID. Проект служит общей точкой сериализации, включая изменения членства и закрытие. Старый прямой DML уже держит строку задачи/заявки: его существующий guard получает проект через `NOWAIT` и сообщает конфликт `PT409`, если проект занят. Он не ждёт в обратном порядке. RPC сроков сохраняет сигнатуру, но получает проект перед задачей. Прямые запросы старого клиента без сравнения версии по-прежнему не гарантируют обнаружение последовательно потерянной правки; новый клиент обязан использовать версионный RPC.
6. RPC требуют ожидаемые версии. Сначала проверка версии, затем сравнение значений. Повтор с текущей версией и теми же значениями — no-op без события. Повтор со старой версией после успешного изменения — **конфликт**, даже если полезная нагрузка совпадает. Реестра request_id нет; сетевой таймаут требует перечитать состояние. Создание также требует версию контейнера. Не обещается идемпотентность создания по произвольному повтору.
7. Бэклог хранит порядок отдельно от `tasks`: это закрытая таблица, поэтому старый прямой UPDATE задачи не может обойти права на порядок. Клиент не пишет `backlog_rank` в задачу. Завершённые задачи и задачи в открытом составе спринта исключаются из текущего бэклога. Повторно открытая задача без открытого состава возвращается в бэклог; её прежний спринт не переписывается.
8. Планируемый состав спринта изменяют участники; состав активного — только управляющий планированием. Старт и закрытие — управляющий. Один активный спринт на проект. При выходе из scrum активный спринт нужно завершить/отменить. Завершение/отмена требуют решения для каждой незавершённой задачи: бэклог либо конкретный планируемый спринт того же проекта. Перенос сохраняет UUID задачи.
9. При старте сохраняется неизменяемый снимок состава/оценок. При закрытии — отдельный снимок итогов и удалённых/исключённых элементов. Идентификатор исходной задачи и снимки переживают удаление самой задачи; живой FK обнуляется. Последующие оценки, повторное открытие и удаление не меняют закрытые результаты. Story Points и часы хранятся и суммируются раздельно; NULL — не оценено, не ноль. Исторические события не создаются задним числом и не являются оценкой качества/труда человека.
10. Закрытый проект доступен для чтения; планирование и задачи в нём не меняются. Занятый этап нельзя переопределить с другой семантикой: нужен новый этап и явный атомарный перенос при архивировании. Нельзя привязать задачи/этапы/спринты разных проектов. Удаление проекта остаётся существующей отдельной операцией, каскадно удаляющей его данные; сохранение результатов относится к удалению **задач**, не к удалению всего проекта.

### Точный API этапа 1 для Клода

Имена и порядок параметров соответствуют SQL; при `supabase.rpc` передавать **именованные** аргументы. Все RPC доступны только `authenticated`; это не заменяет проверок членства внутри функций. Возвращается одна строка соответствующей таблицы, при ошибке вся операция откатывается.

| RPC | Параметры | Результат / права |
| --- | --- | --- |
| `update_project_planning` | `p_project_id uuid, p_expected_version bigint, p_mode text, p_goal text, p_definition_of_done text, p_wip_mode text, p_delegate_to_roles boolean` | `project_planning`; полная замена настроек, управляющий; смена делегирования только автор |
| `set_project_role` | `p_project_id uuid, p_expected_version bigint, p_user_id uuid, p_role text, p_assigned boolean` | `project_planning` с новой версией; только автор; PO/SM максимум по одному |
| `upsert_project_stage` | `p_project_id uuid, p_expected_planning_version bigint, p_stage_id uuid, p_expected_version bigint, p_name text, p_position integer, p_category text, p_status_value text, p_policy text, p_wip_limit integer` | `project_stages`; создание: ID NULL, версия этапа 0; управляющий |
| `archive_project_stage` | `p_project_id uuid, p_expected_planning_version bigint, p_stage_id uuid, p_expected_version bigint, p_target_stage_id uuid` | `project_stages`; управляющий; цель обязательна при наличии задач, перенос атомарен |
| `edit_task_planning` | `p_task_id uuid, p_expected_version bigint, p_stage_id uuid, p_story_points integer, p_planned_hours numeric` | `tasks`; текущий участник; полные новые значения полей, версия `tasks.planning_version` |
| `reschedule_task_secure` | прежние `p_task_id, p_expected_start_at, p_expected_due_at, p_new_start_at, p_new_due_at` | прежний API Ганта; порядок блокировок исправлен, timestamptz без округления/смены зоны |

Чтение: SELECT `project_planning`, `project_stages`, `project_roles` под RLS текущего участника. При отсутствии настроек клиент использует defaults из решения 2. Списки этапов исключают `archived_at IS NOT NULL`, но для истории хранятся все. Активные `position` и эффективные статусы уникальны; перестановка существующих позиций требует свободной промежуточной позиции и свежих версий. WIP — число **незавершённых** задач этапа; в soft клиент показывает превышение по фактическому количеству и `wip_limit`, сервер его не запрещает. Приватные политики и DoD не попадают в публичный listing.

Story Points: NULL либо 1/2/3/5/8/13/21. Плановые часы: NULL либо >0 и <=2000, не более двух десятичных знаков; произвольное округление не выполняется. `PT409` — перечитать сущность/версию и согласовать повтор, `42501` — нет доступа, `23514` — нарушено правило, `23505` — занята уникальная роль/позиция/статус. Для прежнего guard завершённого проекта сохранена ошибка `P0001`. На прямом UPDATE версии увеличиваются сервером, клиент не присваивает их самостоятельно.

### Применение владельцем (после итоговой приёмки этапа 2)

1. Проверить сохранённую копию основной базы и актуальную цепочку миграций; не переносить staging поверх production. Выполнить только чтение `supabase/diagnostics/ER-012-planning.sql`, сравнить владельцев/настройки/триггеры с миграциями проекта. Legacy NULL-время завершения не равно ошибке; противоречивые даты/старые отметки требуют отдельного решения, скрипт их не исправляет.
2. Применить **только новую** миграцию этапа 1 как одну транзакцию, с учётом lock/statement timeout. В существующих проектах режим остаётся simple; массового заполнения настроек/истории нет. Повтор всей старой цепочки не нужен. Новая миграция рассчитана на однократную регистрацию: повторный DDL получает ошибку и откатывается, не удаляет таблицы для повторного запуска.
3. При ошибке остановиться, сохранить текст ошибки без секретов, проверить откат транзакции и schema drift. Не удалять данные и не обходить ограничения. При сетевом таймауте сначала проверить, зафиксировалась ли миграция; не повторять вслепую.
4. После будущего применения проверить ACL внутренних функций, доступы участника/постороннего, обычное создание/статус/даты задач старым сайтом. Реальные проверки выполняет владелец отдельно; агент их не объявляет пройденными.
