## Подтверждённые причины и исправления

**Время сообщений.** На всей цепочке baseline → прежние миграции → три ER-012 воспроизведено: INSERT принимает клиентские `created_at`/`edited_at`; старый guard запрещает изменение `created_at` при UPDATE, но доверяет произвольному `edited_at` и допускает его повторное использование. В цепочке отсутствует включение `project_messages` в `supabase_realtime`.

`20261114130000_project_message_server_time.sql` добавляет отдельный BEFORE-триггер `trg_00_project_message_server_time`. Он выполняется перед неизменённым `trg_phase8_guard_project_messages`: PostgreSQL упорядочивает триггеры одного вида по имени. [Документация PostgreSQL](https://www.postgresql.org/docs/current/sql-createtrigger.html).

- INSERT: `created_at = clock_timestamp()` независимо от клиентского значения; `edited_at = NULL` для обычного сообщения. Для допустимого прежним guard INSERT уже удалённой строки — серверная дата удаления.
- UPDATE: `created_at` возвращается к прежнему значению; при фактическом изменении текста или признака удаления `edited_at` назначается сервером. При отсутствии такого изменения сохраняется прежний `edited_at`, даже если клиент прислал другой/null.
- Попытка восстановления удалённого сообщения, подмена автора/проекта/родителя и межпроектный ответ по-прежнему проверяются старым guard. Прежние формы `.insert(...)` и `.update({body, edited_at: clientNow})` совместимы; ответы, редактирование, мягкое удаление и скрытие для себя сохранены.
- Новая функция SECURITY INVOKER, владелец postgres, `search_path=pg_catalog, pg_temp`; прямой EXECUTE для PUBLIC/anon/authenticated закрыт, эффективные права проверяются. Ни определения прежних функций, ни RLS/ACL таблиц, ни закрытые ER-SEC-001 функции истории не меняются.
- Миграция проверяет владельца, RLS и ожидаемый BEFORE-guard; при расхождении/коллизии имени/унаследованном EXECUTE прекращает собственную транзакцию. Таймаут блокировки 5 с, выполнения 60 с. Повторно поверх уже созданной функции её запускать не следует.

**Существующие сообщения и история не переписаны. Новое правило не подтверждает достоверность старых клиентских дат.** Даже первая настоящая правка старой строки сохраняет её прежний `created_at`; серверная отметка правки не превращает дату создания в проверенную.

**Чтение истории.** Старое обновление только последних 50 строк теряло 25 промежуточных сообщений из 75 новых. Курсор `created_at <= oldest` без порядка UUID застревал на группе одинаковых дат. Эти запросы воспроизведены на синтетике. В клиенте старые загруженные строки и отметки скрытия не перечитывались при обновлении.

Теперь `projectChatRead.ts` использует порядок `(created_at DESC, id DESC)` и строгий курсор этой пары. Сохраняются исходные микросекунды PostgreSQL, без усечения даты курсора JavaScript до миллисекунд. Обновление проходит страницами весь загруженный диапазон, включая всю нижнюю группу одинаковых дат; ранее не загруженная история остаётся у кнопки «Показать предыдущие сообщения». Отметки скрытия перечитываются порциями, ошибка их загрузки не раскрывает скрытые строки. Недоступные строки убираются из перечитанного диапазона, а параллельно догруженная более ранняя история сохраняется.

Чтения обновления сериализованы; ревизия локальных подтверждённых действий не даёт старому ответу затереть их. Смена проекта размонтирует прежний экземпляр, смена аккаунта немедленно скрывает данные/черновик и игнорирует поздние результаты. Позиция читаемого сообщения сохраняется по DOM-якорю, в том числе при изменении высоты/скрытии сообщений выше. Неизменённый результат не запускает повторное выравнивание прокрутки: этот дополнительный дефект был воспроизведён старым браузерным тестом перехода к новым сообщениям и исправлен.

Механизм отправки Claude сохранён: клиентский UUID, явный повтор с тем же UUID, после неопределённого ответа/`23505` — SELECT доступной строки по UUID. Нет автоматического повторного INSERT и нет признания одной ошибки уникальности доказательством успеха. Новых возможностей чата и глобальных переводов нет.

## Realtime и общая рабочая зона

`20261114131000_project_message_realtime.sql` добавляет только `public.project_messages` в уже существующую явную публикацию `supabase_realtime`; если таблица уже включена, не добавляет повторно. Требует включённых INSERT/UPDATE и RLS. Не создаёт широкую публикацию, не меняет её флаги, права, политики, replica identity и прежнюю `notifications`.

Клиент подписан только на INSERT/UPDATE `project_messages` с фильтром `project_id`, в канале проекта и аккаунта. Событие лишь инициирует чтение через прежнюю RLS; содержимое WS-пакета напрямую в список не добавляется. Ранние и повторные уведомления объединяются, на SUBSCRIBED/восстановлении выполняется сверка. Сохранены открытие, focus/visibility и резервное обновление каждые 30 секунд при видимой вкладке. Мягкое удаление — UPDATE; физический DELETE и скрытие в другой вкладке согласуются резервным чтением. Таблица скрытий в публикацию не добавлялась.

По документации Postgres Changes проверяет разрешения каждого подписчика на события; публикация — только часть настройки. Это основание сохранить RLS, а не доказательство работы основной площадки. [Supabase: Postgres Changes](https://supabase.com/docs/guides/realtime/postgres-changes). Права действующего участника/владельца и отсутствие чтения у гостя, постороннего и исключённого проверены в PGlite. **Реальная доставка и отсутствие содержимого закрытого проекта в реальном WebSocket исключённого пользователя ещё не проверены.**

Статически общие компоненты рабочей зоны, страницы задач, доски и planning из принятого ER-012 не заменены. Сохранены `stage_id`, оценки, CAS/WIP, изоляция сессии, `?task=` и переходы к задачам. В общем ui-harness сохранены фиктивные настройки, запрет env-файлов и внешних запросов, прежние planning/RPC mock-пути; добавлена только адресная обработка курсора чата в strict mode. В новом тесте WS имитируется внутри Playwright без соединения с сервером. Гант/календарь/декодер файлов не изменены; прежние успешные широкие наборы не запускались заново без причины.

## PostgREST: два разных незавершённых события

Прочитаны весь `scripts/tests/planning-postgrest.mjs` и сохранённый `test-results/planning-postgrest-1794659022626.txt`. Журнал содержит `FAIL PostgREST startup failed` и остановку `er012-ui-rest-1794659022626`/`er012-ui-pg-1794659022626`. По предыдущему отчёту PostgreSQL принял схему, PostgREST подключился и заполнил cache, но проверка HTTP из Node не достигла успешного ответа. Все шесть HTTP-сценариев остались до точки выполнения. Это **первоначальная транспортная проблема**.

После неё автоматическая проверка разрешений отклонила отдельный повторный запуск диагностического PostgREST (`blocked by policy`, подробная причина не сообщена). Эта команда не выполнялась и не является причиной первоначального HTTP-отказа. **В данном этапе отклонённый запуск не повторялся ни другой оболочкой, ни другим инструментом; Docker и полный ER-007 не запускались.**

Статически в readiness-loop видна потеря диагностической информации: исключения и неуспешные HTTP-статусы не записываются. По этому коду и трём строкам журнала нельзя установить, был ли это маршрутизатор Docker Desktop, порт, HTTP-ответ или таймаут. Исправление причины не выдумывалось; скрипт не менялся и не объявляется прошедшим. Следующее разрешённое продолжение должно сначала сохранять конкретный статус/код ошибки readiness, затем устранить установленную причину в разрешённом окружении, без обхода запрета.

Конечный перечень оставшихся HTTP/конкурентных проверок:

1. Доступность локального HTTP и соответствие JWT роли; именованные параметры RPC и сохранённый этап, прочитанный настоящим REST.
2. Строгий WIP через RPC и старый PATCH; anon/посторонний, закрытые внутренние функции и stale CAS. Отдельно гонка двух перемещений в последний WIP-слот через разные соединения.
3. Атомарная перестановка этапов и замена PO/SM: конфликт версий/неучастник не оставляет частичного результата; конкурентные операции на одном проекте имеют один согласованный итог.
4. Два одновременных создания с одним UUID: один спринт/событие, одинаковый подтверждённый результат; другой payload и другой пользователь не получают чужой результат; приватный реестр недоступен.
5. Разные UUID с одной ожидаемой версией: один commit и один конфликт.
6. Закрытие, получение подтверждения и явный повтор: снимок неизменен после правок/удаления задачи; отсутствие подтверждения не трактуется как успех. Дополнительно одновременное закрытие и изменение состава/задачи.
7. Для чата на полной цепочке с двумя новыми миграциями: REST Insert/Update времён, старый клиент, `23505` + разрешённый SELECT, RLS после исключения, курсор с одинаковыми датами. SQL-адаптер текущего теста не является проверкой синтаксиса/поведения настоящего PostgREST.

Прежние семь многосессионных PostgreSQL-сценариев ER-012 относятся к прежнему серверному снимку; новые операции они не доказывают. Реальная Supabase Realtime, Auth, письма/восстановление пароля, Storage, физическая мобильная клавиатура и сетевые задержки основной площадки не проверены. Чтение загруженного диапазона стоит порядка числа загруженных страниц; производительность длинной переписки и массовые подписки не измерены. До публикации остаются адресная приёмка этих границ и фактическая диагностика, а не новый общий аудит.

## Короткая ручная приёмка и действия при ошибке

1. На отдельном согласованном тестовом проекте два действующих участника: отправить, ответить, изменить, мягко удалить; скрытие видно только выполнившему его пользователю. Проверить прежний опубликованный клиент после SQL. Даты создания при изменении остаются прежними, время настоящей правки серверное.
2. Проверить фактическую WS-подписку двумя аккаунтами, затем посторонним и исключённым участником: содержимое закрытого проекта не приходит и не читается REST. Сам факт появления новой строки через polling не считать доказательством WS-доставки.
3. Разорвать и восстановить соединение, обновить фокус: сообщения/старые правки догружаются. В синтетической среде отдельно проверить больше 50 новых и границу одинаковых дат. При чтении выше низ не навязывается, кнопка новых ведёт к ним, история догружается без дублей.
4. Потерянный ответ проверять на синтетике: сохранённая строка найдена по UUID; после неудачной проверки явный повтор использует тот же UUID. Отсутствующая/недоступная строка после `23505` не показывается отправленной.
5. Сменить проект/аккаунт во время чтения и отправки: старый список/черновик/ответ не попадает в новый. Проверить 360 px, клавиатуру, Escape, reduced motion; затем этап доски/оценку/общую карточку/ссылки к задаче, Гант и календарь.

При ошибке SQL остановиться на первом файле и разобрать расхождение, не ослаблять RLS/EXECUTE и не очищать данные. При ошибке UI сохранить новые данные и вернуть совместимую принятую версию приложения; не возвращать версию без nearby-pack-v1 декодера. Старый чат может продолжать polling при отказе Realtime. Не снимать триггер серверного времени и не восстанавливать старый дамп поверх новых сообщений ради отката интерфейса. Если отказ касается этапов ER-012, действуют ограничения отката из его отчёта.
