## 3. Что зависит от облака — инструкции владельцу (я ничего не менял)

Назначение передаётся в письмо как часть адреса возврата: `https://<сайт>/auth/callback?type=signup|magiclink|recovery&next=<закодированный путь>`. Прежние ссылки уже содержали `?type=…`, новый параметр добавлен тем же способом.

Дополнение: письмо со страницы «Сброс пароля» во время начатого восстановления теперь тоже несёт `next`. Требование к списку адресов то же (п. 1). Cookie `pw_step_next` — локальная настройка браузера (`Path=/`, `SameSite=Lax`, 30 минут), облачных изменений она не требует.

1. **Список разрешённых адресов возврата.** Supabase Dashboard → Authentication → URL Configuration → Redirect URLs.
   - Проверить, что адрес обратного вызова с параметрами разрешён, например `https://<сайт>/auth/callback**`. Для `www` и адресов предпросмотра, если их используют, — отдельные записи.
   - Если адрес не разрешён, Supabase молча ведёт на Site URL. Тогда страница `/auth/callback` не открывается, и это касалось бы и прежних ссылок.
   - Ничего не удалять. Если запись уже допускает `/auth/callback` с любым запросом, менять нечего.
2. **Шаблоны писем.** Authentication → Email Templates: «Confirm signup», «Magic Link», «Reset Password».
   - Ссылка должна строиться из `{{ .ConfirmationURL }}`: в нём есть `redirect_to`.
   - Если шаблон собирает адрес вручную, например из `{{ .SiteURL }}`, параметр `next` теряется. Тогда работает только запасной вариант в том же браузере (1 час).
   - Шаблоны с `token_hash` нынешняя страница обратного вызова не обрабатывает — это не новое ограничение.
3. **Ручная проверка на реальном сайте** — после публикации, отдельно, на проверочном адресе почты:
   1. Гость → главная → «План работ» → «Создать аккаунт» → письмо → ссылка в том же браузере. Ожидание: онбординг → «План работ» проекта, если проект есть; иначе окно с созданием и поиском проекта.
   2. Та же ссылка в другом браузере. Ожидание: тот же результат, если пп. 1–2 настроены; иначе — только онбординг и профиль.
   3. «Получить ссылку для входа» для существующего пользователя.
   4. «Забыли пароль?» → новый пароль → раздел. До смены пароля другие страницы недоступны.
   5. В журналах Auth убедиться, что `redirect_to` принят, а не заменён на Site URL.

   До этой проверки сценарии 1.2–1.5 **не считаются проверенными на реальном Auth**.

## 4. Ограничения

- В другом браузере или на другом устройстве назначение сохраняется только при выполнении пунктов 1–2 раздела 3. Запасная копия работает лишь в том же браузере, час, один раз.
- ~~Уход со страницы обязательной смены пароля терял раздел~~ — исправлено (строка 1.10).
- Продолжение шага пароля хранится в cookie этого браузера 30 минут — столько же, сколько сам маркер шага. Когда маркер истекает, шаг заканчивается, как и раньше.
- Cookie доступна скриптам страницы (не `HttpOnly`): её ставит клиентский `/auth/callback`, как и прежние маркеры. Это не право доступа — каждый читатель принимает только путь этого сайта вне `/auth`, а права на проект проверяются отдельно.
- Если вошедший пользователь с ещё действующим маркером восстановления откроет «Сброс пароля», маркер теперь не снимается: сначала нужно сохранить новый пароль. Это сделано намеренно (строка 1.11).
