# Режимы работы проекта, спринты и оценки: сценарии, модель интерфейса и контракт для Codex

Дата: 13 ноября 2026 года. Состояние: **только проектирование**. Ничего из описанного ниже не реализовано — ни на сервере, ни в интерфейсе. Временное хранение в localStorage или работа на моках не будет выдаваться за многопользовательскую функциональность. Порядок такой: Codex реализует серверную часть по этому контракту с тестами в PGlite, затем подключается интерфейс.

Номер задачи не назначен. В исходной карте 1.2 и `docs/ROADMAP.md` заняты ER-000…ER-011 и ER-SEC-001. Предложение — следующий свободный номер (ER-012), но назначает его владелец или Codex при обновлении дорожной карты (раздел 12).

## 2. Пользовательские сценарии

1. **Автор проекта выбирает режим.** В настройках рабочей зоны: «Простые задачи», «Kanban», «Scrum / спринты» или «Свой процесс». Существующий проект без выбора работает как сейчас («Простые задачи»). Календарь и диаграмма Ганта доступны в любом режиме.
2. **Kanban.** У колонок видны правила работы («Что значит „Готово“») и лимит незавершённой работы: «В работе 3 / 3». При превышении лимита показывается предупреждение или отказ — в зависимости от выбранной строгости. Перенос по-прежнему возможен перетаскиванием, клавиатурой и кнопками.
3. **Scrum.**
   - Владелец продукта формулирует цель продукта и упорядочивает бэклог.
   - Команда планирует спринт: цель, даты, набор задач и их оценки, видна доступная ёмкость.
   - В спринте доска показывает задачи спринта.
   - По окончании автор (или назначенное лицо, раздел 8) завершает спринт. Для каждой незавершённой задачи он явно выбирает: вернуть в бэклог или перенести в следующий спринт.
   - Видны график оставшейся работы и результаты прошлых спринтов.
4. **Свой процесс.** Автор задаёт этапы — например, «Нужно сделать → Расчёт → Проверка у руководителя → Готово». Каждый этап отнесён к одной из базовых категорий и, при необходимости, к существующему значению статуса.
5. **Оценки в любом режиме.** У задачи есть необязательные Story Points (1, 2, 3, 5, 8, 13, 21) и отдельно плановые часы. «Не оценено» отличается от любого значения. Фактическое время берётся из вклада, загрузка — с учётом доступности участников.
6. **Смена режима.** Ничего не удаляется: задачи, история, оценки и завершённые спринты сохраняются. Переход из Scrum при активном спринте требует сначала завершить или отменить спринт.

## 3. Модель интерфейса (для последующего подключения)

| Элемент | Режимы | Поведение |
| --- | --- | --- |
| «Режим работы» в настройках рабочей зоны | все | Выбор и пояснение последствий перед подтверждением. Сервер проверяет правила перехода (раздел 7) |
| Доска | все | Простые задачи — три текущие колонки. Kanban — колонки этапов с лимитами и правилами. Scrum — задачи активного спринта. Свой процесс — колонки этапов. Ручной сортировки внутри колонки нет |
| Бэклог (список) | Scrum | Упорядоченный список. Порядок меняется перетаскиванием в списке или кнопками «Выше/Ниже» и клавиатурой через серверную операцию `reorder_backlog`. Оценка — прямо в строке |
| Панель спринта | Scrum | Цель, даты, состояние, взятый объём (баллы и часы отдельно), ёмкость команды с источником данных |
| Окно завершения/отмены спринта | Scrum | Список незавершённых задач с обязательным выбором действия для каждой. Без выбора подтверждение недоступно |
| Карточка и окно задачи | все | Поля «Story Points» (список значений + «Не оценено»), «Плановые часы», «Факт по вкладу» (сумма `contributions.hours`, только чтение) |
| «Спринты» и графики | Scrum, Kanban | Scrum: оставшаяся работа и результаты спринтов. Kanban: накопительный поток и время цикла — только начиная с даты включения режима |
| Встречи | Scrum | Кнопки «Запланировать планирование / Daily Scrum / обзор / ретроспективу» создают события проекта с привязкой к спринту. Участники выбираются явно |

Тексты — с обращением на «Вы», без рейтинга людей. Рядом с графиками пояснение: «Баллы — относительная оценка задач командой, не мера работы человека».

## 4. Scrum: правила

- **Цель продукта** — текст в настройках планирования проекта; изменения пишутся в историю.
- **Бэклог** — задачи проекта вне незакрытых спринтов, кроме задач со статусом `done`. Порядок задаёт `tasks.backlog_rank`. Задачи без ранга стоят в конце по дате создания.
- **Роли** Product Owner, Scrum Master и команда — это атрибуты участия, **не права доступа**. Назначить можно только участника проекта. Product Owner и Scrum Master — не больше одного на проект. Роли не дают и не отнимают прав: права остаются такими, как в разделе 8.
- **Спринт:** номер, название, цель, плановые даты начала и конца. Состояния: `planned → active → completed`; `planned/active → cancelled`.
  - В первой версии **один активный спринт на проект** (уникальный частичный индекс). Запланированных может быть несколько.
  - Даты спринта — интервал `timestamptz`, конец позже начала.
- **Планирование:** задачи добавляются в `planned` или `active` спринт.
  - Добавление и удаление после старта — изменение состава. Оно пишется в историю с баллами на момент изменения и показывается на графике.
  - Задача может состоять только в одном незакрытом спринте.
- **Критерии готовности (Definition of Done)** — текст проекта, показывается в окне задачи и при переносе в «Готово». Автоматически не проверяется.
- **Встречи** — события `project_events` с типами `sprint_planning`, `daily_scrum`, `sprint_review`, `retrospective` и полем `sprint_id`. Участники — только явно добавленные (`project_event_participants`). Исполнитель задачи участником встречи не считается.
- **Завершение спринта:**
  - Сервер требует решение по каждой незавершённой задаче: `backlog` или `next_sprint` (указанный `planned`-спринт).
  - Задачи **не завершаются автоматически**; их статус не меняется.
  - Перенос не создаёт копию задачи: в старом спринте фиксируется итог `moved`, в новом создаётся новая запись участия **той же** задачи.
- **Отмена спринта** — то же явное решение по задачам, причина обязательна. Завершённые задачи остаются завершёнными.
- **История:** изменения состава, оценок, целей, дат и состояний спринта — события `project_activity` с автором и старыми/новыми значениями.
- **График оставшейся работы** строится из снимка состава при старте и последующих событий: завершение задачи, изменение состава, изменение оценки.
  - Отдельно по баллам и по плановым часам.
  - Для спринтов до включения функции данных нет — показывается «Нет данных». Прошлое из сегодняшнего состояния задач не восстанавливается.
- **Результаты завершённых спринтов:** взятый объём, завершённый объём, изменения состава, перенесённые задачи. Только из зафиксированных событий.

## 5. Kanban: правила

- Колонки — этапы `project_stages` (раздел 6). При включении Kanban создаются три этапа по текущим колонкам: `todo`, `doing`, `done`.
- **Правила работы** (`policy`) — текст этапа: что означает войти в колонку и выйти из неё.
- **Лимит незавершённой работы** (`wip_limit`) — целое ≥ 1 или пусто. Строгость `wip_mode`:
  - `soft` (по умолчанию): перенос разрешён, интерфейс и ответ сервера сообщают о превышении, событие пишется в историю;
  - `hard`: сервер отклоняет перенос сверх лимита с понятной причиной.

  Для этапов категории `done` лимит не применяется.
- Проверка лимита идёт под блокировкой строки этапа: два одновременных переноса не превысят строгий лимит.

## 6. Свой процесс: этапы и совместимость со статусами

`project_stages`: название, позиция, категория `todo|doing|done`, необязательное `status_value` (существующее значение `tasks.status`), правила и лимит.

- `tasks.status` продолжает хранить значение, понятное старым клиентам. При переносе в этап сервер записывает `status = coalesce(stage.status_value, stage.category)` и `tasks.stage_id = stage.id`.
- Если старый клиент меняет только `status`, триггер находит этап проекта:
  1. с таким `status_value`;
  2. если такого нет — с такой же категорией и наименьшей позицией.

  Если подходящего этапа нет, `stage_id` очищается, и задача показывается в «Других статусах», как сейчас.
- Значения вроде `review` безопасно отображаются в свой этап через `status_value = 'review'`, без переименования данных.
- Удалить этап нельзя, пока в нём есть задачи. Архивирование требует указать этап для переноса задач; перенос атомарен и пишется в историю.
- `completed_at` по-прежнему ставится при переходе в категорию `done` и снимается при выходе из неё.

## 7. Смена режима

| Из → в | Правило |
| --- | --- |
| Любой → Простые задачи | Разрешено. Этапы, лимиты, спринты, роли, оценки сохраняются и скрываются. Доска показывает три базовые колонки и «Другие статусы» |
| Простые → Kanban / Свой процесс | Разрешено. Если этапов нет, создаются три базовых. `stage_id` задач заполняется по правилу раздела 6 |
| Kanban ↔ Свой процесс | Разрешено. Этапы общие; в Kanban видны лимиты и правила, в своём процессе — дополнительные этапы |
| Любой → Scrum | Разрешено. Бэклог — все незавершённые задачи вне спринтов. Спринты не создаются автоматически |
| Scrum → любой при **активном** спринте | **Отклоняется** с причиной «Сначала завершите или отмените спринт». Решение по задачам принимается в окне спринта |
| Scrum → любой без активного спринта | Разрешено. Запланированные спринты остаются в состоянии `planned` и скрываются; завершённые доступны для чтения в «Спринтах» |
| Повторное включение режима | Восстанавливает прежние этапы, лимиты, роли и спринты: они не удалялись |

Каждая смена режима — событие `project_mode_changed` с автором, прежним и новым режимом. В завершённом проекте (`listings.completed_at`) смена режима и все изменения планирования запрещены, как и изменения задач.

## 8. Права

- **Чтение** новых таблиц — участники проекта: автор и принятые участники, то же определение, что в RLS задач. Гость и посторонний не видят ничего.
- **Изменения** — только через RPC `security definer` с проверкой `auth.uid()`, членства и незавершённости проекта. Прямые INSERT/UPDATE/DELETE для `authenticated` закрыты, как в ER-SEC-001.
- **Управление планированием** (режим, этапы, лимиты, роли, цель продукта, критерии готовности, создание/старт/завершение/отмена спринта) — в первой версии только автор проекта. Так уже устроен дедлайн проекта.
- Расширение на назначенных Product Owner или Scrum Master — **отдельный явный флаг** `project_planning.delegate_to_roles`, включаемый автором. Название роли само по себе прав не даёт.
- **Работа с задачами** (перенос между этапами, оценки, добавление и удаление задач в `planned`-спринт, порядок бэклога) — любой участник проекта, как сейчас с задачами. Порядок бэклога можно ограничить автором и Product Owner флагом `backlog_order_restricted`.

## 9. Таблицы и поля

Все `timestamptz`; `created_at default now()`; внешние ключи с `on delete cascade` от проекта, кроме ссылок на пользователей. Для всех таблиц включён RLS.

```text
project_planning                       -- одна строка на проект; отсутствие строки = «Простые задачи»
  project_id uuid pk → listings(id)
  work_mode text not null default 'simple' check (work_mode in ('simple','kanban','scrum','custom'))
  product_goal text, definition_of_done text
  wip_mode text not null default 'soft' check (wip_mode in ('soft','hard'))
  delegate_to_roles boolean not null default false
  backlog_order_restricted boolean not null default false
  version integer not null default 1, updated_by uuid, updated_at timestamptz

project_roles
  project_id uuid, user_id uuid, role text check (role in ('product_owner','scrum_master','developer'))
  assigned_by uuid, assigned_at timestamptz
  primary key (project_id, user_id, role)
  unique (project_id) where role = 'product_owner'; unique (project_id) where role = 'scrum_master'

project_stages
  id uuid pk, project_id uuid, name text not null (1–60), position integer not null
  category text not null check (category in ('todo','doing','done'))
  status_value text null                -- существующее значение tasks.status
  wip_limit integer null check (wip_limit >= 1), policy text null
  archived_at timestamptz null, version integer not null default 1
  unique (project_id, position) where archived_at is null
  unique (project_id, status_value) where archived_at is null and status_value is not null

tasks (новые необязательные столбцы; старые клиенты их не передают)
  stage_id uuid null → project_stages(id)
  story_points smallint null check (story_points in (1,2,3,5,8,13,21))   -- null = «Не оценено»
  planned_hours numeric(6,2) null check (planned_hours > 0 and planned_hours <= 2000)
  backlog_rank bigint null              -- с промежутками; уплотнение — отдельная серверная операция

sprints
  id uuid pk, project_id uuid, number integer not null, name text, goal text
  starts_at timestamptz not null, ends_at timestamptz not null check (ends_at > starts_at)
  state text not null default 'planned' check (state in ('planned','active','completed','cancelled'))
  started_at, started_by, closed_at, closed_by, close_reason text
  version integer not null default 1, created_by uuid
  unique (project_id, number); unique (project_id) where state = 'active'

sprint_items                           -- участие задачи в спринте; задача не копируется
  id uuid pk, sprint_id uuid, task_id uuid, project_id uuid
  added_at, added_by, points_at_add smallint null, hours_at_add numeric(6,2) null
  removed_at timestamptz null, removed_by uuid null
  outcome text null check (outcome in ('done','backlog','moved','removed'))
  unique (task_id) where removed_at is null and outcome is null   -- одно открытое участие на задачу

sprint_snapshots                        -- неизменяемый снимок при старте спринта
  sprint_id uuid pk, taken_at timestamptz, items jsonb  -- [{task_id, points, hours, status}]
  total_points integer, total_hours numeric, unestimated_count integer

project_events (новый столбец)  sprint_id uuid null → sprints(id)
project_event_participants
  event_id uuid, user_id uuid, added_by uuid, added_at timestamptz, response text null
  primary key (event_id, user_id)       -- user_id обязан быть участником проекта
```

Ограничения проверяются и на сервере, и в CHECK. `stage_id` должен принадлежать тому же проекту, что и задача (проверка в триггере). `sprint_items.project_id` совпадает с проектом задачи и спринта.

## 10. Операции (RPC)

Общие правила для каждой операции:
- проверка `auth.uid()`, членства и прав из раздела 8, незавершённости проекта;
- `FOR UPDATE` изменяемых строк; сравнение ожидаемой версии или прежних значений, иначе `PT409` без изменений;
- одно событие истории в той же транзакции;
- `revoke all … from public, anon; grant execute … to authenticated`; повтор с теми же данными ничего не дублирует.

| Операция | Суть |
| --- | --- |
| `set_project_work_mode(p_project_id, p_expected_version, p_mode)` | Правила раздела 7. При необходимости создаёт базовые этапы и заполняет `stage_id` |
| `update_project_planning(p_project_id, p_expected_version, p_product_goal, p_definition_of_done, p_wip_mode, p_flags…)` | Цель продукта, критерии готовности, строгость лимитов, флаги делегирования |
| `set_project_role(p_project_id, p_user_id, p_role, p_assigned boolean)` | Проверяет, что пользователь — участник; единственность PO и SM |
| `upsert_project_stage(…)`, `archive_project_stage(p_stage_id, p_expected_version, p_move_to_stage_id)` | Этапы, лимиты, правила; архивирование с атомарным переносом задач |
| `move_task_to_stage(p_task_id, p_expected_stage_id, p_expected_status, p_stage_id)` | Ставит `stage_id`, `status`, `completed_at`. Проверяет лимит под блокировкой этапа. Возвращает признак превышения мягкого лимита |
| `set_task_estimate(p_task_id, p_expected_points, p_points, p_expected_hours, p_hours)` | NULL — допустимое значение «Не оценено». Событие `task_estimate_changed` |
| `reorder_backlog(p_task_id, p_after_task_id, p_before_task_id, p_expected_rank)` | Ставит ранг между соседями; при нехватке промежутка уплотняет ранги проекта в той же транзакции |
| `create_sprint(…)`, `update_sprint(p_sprint_id, p_expected_version, …)` | Даты, цель, название. Пересечение дат с активным спринтом допускается только для `planned` |
| `add_tasks_to_sprint(p_sprint_id, p_expected_version, p_task_ids uuid[])` / `remove_task_from_sprint(…)` | Одно открытое участие на задачу; запись баллов на момент изменения |
| `start_sprint(p_sprint_id, p_expected_version)` | Проверка «нет другого активного», снимок `sprint_snapshots`, событие `sprint_started` |
| `complete_sprint(p_sprint_id, p_expected_version, p_decisions jsonb)` / `cancel_sprint(…, p_reason, p_decisions)` | Решение обязательно для каждой незавершённой задачи (`backlog` или `next_sprint` + `planned`-спринт этого проекта). Неполный или лишний список — ошибка. Статусы задач не меняются |

Перенос сроков остаётся в `reschedule_task_secure`, смена статуса трёх базовых колонок — в существующем пути. В режимах с этапами интерфейс переходит на `move_task_to_stage`.

## 11. История и графики

Новые типы `project_activity` (добавить в список допустимых `append_project_activity_internal`, EXECUTE для клиентов не открывать):

- `project_mode_changed`, `project_planning_changed`, `project_role_changed`;
- `stage_changed`, `task_stage_changed` (с флагом превышения лимита), `task_estimate_changed`;
- `sprint_created`, `sprint_updated`, `sprint_started`, `sprint_scope_changed`, `sprint_completed`, `sprint_cancelled`.

В `metadata` — старые и новые значения, идентификаторы и версия.

| График | Источник | Правило |
| --- | --- | --- |
| Оставшаяся работа спринта | Снимок при старте + события состава/оценок/завершения задач | Две линии: баллы и плановые часы. Неоценённые задачи — отдельным числом, не нулём. Изменения состава отмечены |
| Результаты спринтов | `sprint_items` с итогами и снимки | Взято / завершено / перенесено / удалено. Без «скорости человека» |
| Накопительный поток, время цикла (Kanban) | `task_stage_changed` | Только с даты включения этапов; раньше — «Нет данных» |
| Загрузка | Плановые часы задач спринта по исполнителям против доступности | До ER-004 — только заявленное в профиле с пометкой; при отсутствии — «Недостаточно данных» |

Запрещено:
- переводить баллы в часы фиксированным коэффициентом;
- показывать баллы или скорость как рейтинг участника или оценку студента;
- восстанавливать прошлую работу из текущего состояния задач.

## 12. Согласование с ER-004, ER-005, ER-011 и предложения для документов Codex

- **ER-004.** Ёмкость спринта = сумма пересечений интервалов доступности участника с датами спринта по правилам ER-004 (DST, полночь, асинхронность — отдельно, не круглосуточно). Пока ER-004 не реализован, показывается только «заявлено в профиле: N ч/нед» без расчёта пересечений.
- **ER-005.** События планирования (`sprint_*`, оценки, порядок бэклога) **не являются квалифицирующими результатами** и не повышают показатели. Изменения состава спринта и плана записаны и делают перенос плана прозрачным — это то, чего требует п. 4 и п. 3 раздела 10 карты. Баллы и скорость в отчёте ER-005 не используются как мера работы студента.
- **ER-011.** Планировщик может предлагать черновик: состав спринта, оценки, этапы. Применение — только через эти же RPC после подтверждения пользователем с нужными правами и с повторной проверкой версий. Оценки, предложенные ассистентом и принятые человеком, помечаются в `metadata` события (`source: 'assistant_confirmed'`). Отключение планировщика ничего из этого не удаляет.

Предлагаемая строка для `docs/ROADMAP.md` — её вносит Codex, этот документ дорожную карту не редактирует:

> ER-012 (номер предлагается) | P2 / спроектировано, не реализовано | Режимы проекта (простые задачи, Kanban с лимитами, Scrum с одним активным спринтом, свой процесс с этапами), оценки Story Points/плановые часы, история и графики. Зависит от: F-02/истории (выполнено локально), ER-004 для ёмкости. Контракт: `docs/reports/planning-modes-contract.md`.

## 13. Тесты, которые нужны до подключения интерфейса (PGlite)

1. Существующий проект без строки `project_planning` ведёт себя как сейчас; старый UPDATE `status` работает; `review` сохраняется.
2. Посторонний, гость, ожидающий и исключённый участник не читают и не меняют новые таблицы; прямой INSERT/UPDATE закрыт; EXECUTE функций истории закрыт.
3. Завершённый проект: все новые операции отклоняются.
4. Второй активный спринт невозможен, в том числе при двух одновременных `start_sprint`.
5. Задача не может быть в двух незакрытых спринтах; перенос в следующий спринт не создаёт новую задачу.
6. `complete_sprint` без решения по каждой незавершённой задаче отклоняется; статусы задач не меняются; снимок неизменяем.
7. Story Points вне набора, 0 и отрицательные часы отклоняются; NULL отличается от значения; история содержит старое и новое значение и автора.
8. Строгий лимит не превышается при одновременных переносах; мягкий пропускает и сообщает о превышении.
9. Архивирование этапа с задачами без указания нового этапа отклоняется; с указанием — перенос атомарен.
10. Смена режима при активном спринте отклоняется; после смены ничего не удалено; обратная смена восстанавливает этапы.
11. Устаревшая версия любой операции даёт `PT409` без частичных изменений.
12. Повтор миграции; владельцы, `search_path`, ACL новых функций.

После серверной части — браузерные проверки интерфейса на моках и отдельно приёмка на реальной базе владельцем. Эти результаты не смешиваются.

## 14. Оценка и решения владельца

Ориентировочная сложность — L. Сервер: миграция, RPC, триггер соответствия этапов, тесты PGlite. Интерфейс: настройки, бэклог, спринты, графики.

До реализации нужно решить:
1. Строгость лимитов по умолчанию (`soft` предложено).
2. Делегировать ли управление спринтами назначенным Product Owner или Scrum Master.
3. Ограничивать ли порядок бэклога.
4. Нужен ли учёт ответов участников встреч (`response`) в первой версии.
5. Номер задачи в дорожной карте.
