- Сколько в основной базе старых значений часового пояса (`UTC+3` и т. п.) и пустых значений.

## 3. Моки и реальный Supabase

- **Всё в браузерных тестах — моки.** `scripts/tests/ui-harness.mjs`:
  - собирает и запускает приложение с фиктивным адресом Supabase;
  - отвечает этому адресу моком в памяти: REST с фильтрами `eq`/`is`/`in`, RPC, ответы Auth;
  - отклоняет запросы к остальным хостам, кроме `127.0.0.1`;
  - закрывает любые WebSocket до подключения (`routeWebSocket`), поэтому Realtime не соединяется.
- Мок не воспроизводит RLS, триггеры, историю, защитные проверки и настоящие коды ошибок. Ошибки и задержки подставляются тестом явно.
- `test:storage` использует PGlite — PostgreSQL в памяти. Это не проверка реального Supabase.
- **К основной базе, Auth, Storage и Realtime обращений не было.** Тестовых данных в основной базе не создавалось.
- **Важно про прошлые прогоны.** До этого пакета `navigation-ui.mjs` и `pilot-ui.mjs` не перехватывали WebSocket. В прогонах ER-001 клиент Realtime после входа мог пытаться открыть соединение с `wss://pilot-test.supabase.co`: это фиктивный проект с тестовым ключом, к базе проекта он отношения не имеет. Теперь такие соединения закрываются в тесте.

## 4. Ключевые решения

- **Навигация.**
  - Используется шаблон disclosure (`button` + `aria-expanded` + `aria-controls`), а не `role="menu"`.
  - Одновременно открыто одно меню. Оно закрывается при уходе фокуса, щелчке вне шапки и выборе пункта.
  - Брейкпоинты не менялись.
  - Ссылка на «Этику» скрыта только в подвале: документ и маршрут `/legal/ethics` работают.
- **Термины рынка.** Подписи собраны в `src/lib/marketLabels.ts`:
  - типы: «Заказ на разработку» / «Готовый проект»;
  - статусы объявления: Черновик / Открыто / Закрыто / Отменено;
  - статусы предложения: Новое / В шорт-листе / Выбрано / Отклонено / Отозвано.

  Коды в базе прежние. Замены сделаны по смыслу, не по подстроке; окончания согласованы со средним родом («Объявление закрыто»).
- **Часовой пояс.**
  - `Intl.supportedValuesOf('timeZone')` отдаёт не все синонимы (нет `Europe/Kyiv` и `UTC`) и приводит их к канону по-разному. Поэтому синонимы заданы явной таблицей.
  - Нестандартное значение остаётся в списке как есть и совпадает только с самим собой.
- **Доска.** Используется собственная реализация на Pointer Events, без новой библиотеки: ручка карточки, захват указателя, автопрокрутка у краёв окна.
- **Гант.**
  - Шкала строится по локальным суткам, с учётом перехода на летнее время. Во время перетаскивания шкала фиксируется.
  - Конфликт определяется условием `update` со старыми значениями. При 0 изменённых строк задача перечитывается: если она изменилась — это конфликт, иначе — нет прав.
- **Рекламные места.** Компонент без состояния, эффектов и сетевых запросов. На главной он рендерится на сервере, а в каталогах (это клиентские страницы) входит в их бандл. Размеры резервируются через CSS-переменные.

## 6. Контракт для Codex: серверная часть диаграммы Ганта

**Что делает клиент сейчас.** `saveTaskDates(task, startAt, dueAt)` в `src/lib/taskSchedule.ts`:

1. Проверяет `due ≥ start`.
2. Выполняет `update tasks set start_at, due_at` с условиями `id = …` и старыми значениями `start_at`/`due_at` (`eq`, а для пустых — `is null`), с `select()`.
3. Если изменено 0 строк, перечитывает задачу:
   - задача изменилась — конфликт: показываются свежие даты и сообщение;
   - не изменилась — нет прав.

Переход на RPC (пункт 3 ниже) меняет только эту функцию.

**1. История дат, F-02. Обязательно.**
- В `public.trusted_activity_from_task()` добавить для `UPDATE` запись при условии `new.start_at is distinct from old.start_at or new.due_at is distinct from old.due_at`. Запись отдельная, независимо от ветки статуса.
- Вызов:
  ```
  append_project_activity_internal(new.project_id, 'task_schedule_changed', format('Изменены сроки задачи «%s»', new.title), null, 'task', new.id,
    jsonb_build_object('task_id', new.id, 'task_title', new.title,
      'old_start_at', old.start_at, 'new_start_at', new.start_at,
      'old_due_at', old.due_at, 'new_due_at', new.due_at))
  ```
- Автор — `auth.uid()` внутри `append_project_activity_internal`, как для статусов.
- Добавить `'task_schedule_changed'` в список допустимых `p_type` в `append_project_activity_internal`.
- Сохранить `security definer`, `search_path` и ограничения EXECUTE из `20261110090000_project_activity_execute.sql`. `create or replace` права сохраняет, но тест должен это подтвердить.
- Даты хранить в метаданных как есть, а форматировать в интерфейсе в часовом поясе пользователя. Не форматировать их в SQL во времени сервера.

**2. Проверка порядка дат на сервере. Обязательно.**
- В триггер `BEFORE INSERT OR UPDATE` (например, в `phase8_guard_task_row`) добавить: если обе даты заданы и `due_at < start_at`, то `raise exception 'Дедлайн не может быть раньше начала.'`. Русский текст пройдёт в интерфейс как есть.
- Дополнительная страховка — `CHECK (start_at is null or due_at is null or due_at >= start_at) NOT VALID`.
- `VALIDATE` выполнять только после подсчёта нарушающих строк в основной базе (запрос только на чтение) и решения владельца о них.

**3. Атомарный перенос. Рекомендуется.**
- Функция `public.reschedule_task_secure(p_task_id uuid, p_expected_start_at timestamptz, p_expected_due_at timestamptz, p_new_start_at timestamptz, p_new_due_at timestamptz) returns public.tasks`, `security definer`, `set search_path = public, pg_temp`.
- Проверки:
  - участие в проекте — как в политике «Project members can update tasks»;
  - проект не завершён — как в `guard_completed_project_work`;
  - строка блокируется `select … for update`;
  - ожидаемые значения сравниваются через `is not distinct from`. При расхождении — отдельный различимый код ошибки конфликта, данные не меняются;
  - `due ≥ start`.
- Затем `update`; историю пишет триггер из пункта 1.
- `revoke all … from public, anon; grant execute … to authenticated`.
- Нынешнее условное `update` уже не даёт потерять чужую правку: это один SQL-оператор. RPC нужен ради ясного кода конфликта и одного места для правил.

**4. Необязательно.** `tasks.updated_at` с триггером — для определения конфликтов по другим полям и для Realtime.

**5. Тесты в PGlite** (по образцу существующих тестов истории и хранилища):
- перенос участником создаёт ровно одну запись `task_schedule_changed` с автором, старыми и новыми датами;
- изменение только статуса записи о сроках не создаёт;
- посторонний пользователь не может перенести задачу;
- в завершённом проекте перенос запрещён;
- `due < start` — ошибка с русским текстом;
- расхождение ожидаемых значений — код конфликта, данные не изменены;
- `anon` не может вызвать RPC;
- EXECUTE функций истории по-прежнему ограничен.

**6. После серверной части — клиент:**
- переключить `saveTaskDates` на RPC, если он будет;
- показать изменения сроков в «Истории» из метаданных;
- затем перевести Гант в «готово».

**Не делать:**
- автоматический сдвиг зависимых задач;
- восстановление истории прошлых переносов: источника нет, ROADMAP запрещает восстанавливать вымышленную историю.
