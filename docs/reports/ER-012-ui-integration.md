## Что исправлено

### А. Этапы на рабочей доске

В пакете Claude `tasks.stage_id` менялся только через редактор задачи, а доска использовала фиксированные статусы. Теперь в Kanban, Scrum и собственном процессе колонки строятся по активным `project_stages`, в серверном порядке. Показаны правила и WIP. Перенос указателем, стрелками клавиатуры или выбором этапа вызывает **`edit_task_planning`** с `tasks.planning_version`; Story Points и часы передаются без изменения. Статус и `completed_at` вычисляет сервер, история создаётся триггерами. Ошибка/конфликт снимает оптимистичное перемещение и перечитывает сохранённые данные.

В `simple` сохранены прежние колонки и путь изменения статуса. Задачи без этапа остаются в отдельном разделе «Без этапа», включая известные и неизвестные старые статусы. Переключение режима больше не назначает этапы старым задачам массово. При этом новые INSERT и явная смена статуса старым клиентом по-прежнему сопоставляются **только с точным действующим статусом этапа**. Категория `doing` не делает произвольный статус эквивалентом любому этапу.

Серверный BEFORE-триггер продолжает проверять WIP при прямых INSERT/UPDATE. Дополнительно задача, уже назначенная этапу в настроенном процессе, не может выйти из проверки через очистку `stage_id` и произвольный статус. Завершена только задача со статусом `done`; повторное открытие очищает `completed_at`. Архивный/чужой этап запрещён. Новая миграция не переписывает существующие строки или историю.

### Б. Одна транзакция для порядка и роли

Подтверждены обе цепочки частичного сохранения из отчёта Claude: три запроса для перестановки и два для замены PO/SM. Вместо них интерфейс вызывает:

| RPC и точные аргументы | Контракт |
| --- | --- |
| `reorder_project_stages(p_project_id uuid, p_expected_planning_version bigint, p_stage_ids uuid[])` | Полный набор уникальных активных этапов проекта, до 5000. Права управляющего, CAS версии настроек, блокировки, обе фазы перестановки, версии этапов и одно событие истории — в одной транзакции. Результат: строка `project_planning`. |
| `replace_project_lead(p_project_id uuid, p_expected_planning_version bigint, p_role text, p_user_id uuid)` | Только автор проекта; роль `product_owner` или `scrum_master`; новый держатель — действующий участник. `null` явно снимает роль. Удаление/вставка, версия и одно событие — атомарны. Результат: строка `project_planning`. |

Роль `developer` остаётся на прежнем `set_project_role`. Новые RPC не расширяют делегирование. Повтор порядка/роли с актуальной версией и теми же значениями — no-op; **устаревшая версия всё равно конфликтует**. Идемпотентность по UUID для этих двух RPC не обещана. После потери ответа нужно перечитать состояние, не повторять вслепую старую версию.

Порядок блокировок: проект → настройки → затронутые этапы по UUID; для роли — проект → настройки → существующая ведущая роль. Временные позиции не выходят за транзакцию. Переполнение диапазона позиции даёт отказ. Отказ при добавлении истории откатывает и данные, и версии: это проверено искусственным исключением внутри локальной БД.

### В. Однозначный результат создания/закрытия

Эвристика «название + автор + время» удалена. Добавлены:

| RPC и точные аргументы | Результат |
| --- | --- |
| `create_project_sprint_once(p_request_id uuid, p_project_id uuid, p_expected_planning_version bigint, p_name text, p_goal text, p_start_at timestamptz, p_end_at timestamptz)` | Строка `project_sprints`; при точном повторе — сохранённая строка первоначального результата. |
| `close_project_sprint_once(p_request_id uuid, p_sprint_id uuid, p_expected_version bigint, p_cancel boolean, p_reason text, p_decisions jsonb)` | Строка спринта с итоговым снимком; точный повтор возвращает исходный результат. Формат решений прежний: `{task_id,destination:'backlog'}` или `{task_id,destination:'sprint',sprint_id,expected_sprint_version}`. |
| `get_project_planning_request(p_project_id uuid, p_request_id uuid)` | JSON `{request_id,project_id,actor_id,kind,result}` либо `null`. `kind` — `create_sprint`/`close_sprint`. Только собственный запрос и действующее членство. |

Приватная таблица `project_planning_requests` хранит UUID, пользователя, проект, тип, **все типизированные параметры, включая ожидаемые версии**, и результат. Глобальный PK не позволяет использовать UUID для другого пользователя/проекта/операции. Несовпадение параметров — `22023`, без нового объекта и без выдачи чужого результата. Ошибка исходной операции откатывает и запись запроса. Результат и история фиксируются вместе. Повтор проверяет актуальные права; исключённый участник результата не получает. Для закрытого проекта остаётся чтение своего подтверждения, новые записи запрещены.

Создание/закрытие держат блокировку проекта, затем запись запроса, затем используют существующие серверные операции с их порядком блокировок спринтов/задач. PK сериализует совпавший UUID даже для разных проектов. Многосессионное исполнение **новых** операций пока не подтверждено отдельными соединениями — см. ограничения ниже.

В интерфейсе UUID создаётся до отправки. Исходные аргументы сохраняются в `sessionStorage` с ключом пользователя/проекта/операции; при повторе неизменны. Автоматического повторного POST нет. При транспортной/неопределённой ошибке выполняется чтение подтверждения. `null` означает **«результат пока неизвестен»**, поскольку незавершённая транзакция ещё не видна. Закрытое состояние спринта само по себе не доказывает выполнение именно данного запроса. Пользователь может проверить снова или явно повторить тот же UUID с теми же аргументами.

Старые `create_project_sprint` и `close_project_sprint` сохранены для совместимости; у них нет этого механизма повторов. Для новых RPC `PUBLIC`/`anon` EXECUTE закрыт; `authenticated` имеет только разрешённые публичные операции. Служебный `planning_claim_request_internal`, другие внутренние функции истории и прямой доступ клиентов к таблице подтверждений закрыты. Наследуемые эффективные права проверяются миграцией. RLS не отключён.

### Состояние интерфейса

Рабочая зона получает ключ по ID проекта; старые формы/выборы не переносятся в новый проект. Загрузки задач проверяют актуальность поколения/последовательности. Хук планирования отбрасывает старые загрузки, результаты записей и последующие проверки подтверждения после смены проекта/сессии. Эти случаи проверены настоящими переходами Next без перезагрузки документа, с задержанными моковыми ответами.

Доска, карточка, Гант и календарь продолжают использовать общий перечитанный список задач. Неизменённые даты спринта в редакторе сохраняют секунды исходного timestamp; ввод изменённых дат остаётся в часовом поясе устройства. Автопереноса зависимостей и сортировки карточек внутри колонок нет.

## Оставшиеся ограничения и условия публикации

Найденные пробелы А–В исправлены; известного воспроизводимого блокера кода в проверенном объёме не осталось. Однако **публикацию пока не считать принятой**:

1. Завершить адресный тест новых RPC через настоящий локальный PostgREST; отдельно подтвердить гонки UUID/версий, WIP и атомарных операций двумя соединениями. Прежние 7 конкурентных сценариев ER-012 относятся к старому серверному снимку; они не повторялись и не доказывают новые операции. PGlite и HTTP-моки этого не заменяют.
2. Фактическая основная схема/ACL/миграции не читались. Владелец должен выполнить диагностику и сопоставление перед SQL.
3. Реальные Supabase Auth, письма, подтверждение/восстановление, Storage и Realtime не проверялись. Новые planning-таблицы не подписаны на Realtime; отображение обновляется после операции/«Обновить»/reload.
4. `sessionStorage` переживает reload в той же вкладке, но не гарантирует восстановление после закрытия вкладки/очистки/запрета хранилища. Серверные подтверждения бессрочны до удаления проекта; их очистку сейчас не вводили. После утраты UUID нельзя доказывать свой результат по одному названию и времени или слепо создавать заново. Объём реестра подтверждений надо наблюдать при эксплуатации.
