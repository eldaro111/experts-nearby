## 2. Серверные правила и совместимость

Новая миграция [20261112090000_task_schedule.sql](../../supabase/migrations/20261112090000_task_schedule.sql) реализует контракт раздела 6 отчёта Клода:

- Разрешены обе пустые даты, только начало, только дедлайн, равные даты и дедлайн после начала. Дедлайн раньше начала запрещён при INSERT/UPDATE, включая прямой запрос в обход интерфейса: guard-триггер и CHECK.
- CHECK создан **NOT VALID**: несовместимые существующие строки не исправляются и не удаляются. Новые и изменяемые строки проверяются сразу. Поэтому даже изменение другого поля старой несовместимой задачи будет отклонено, пока её даты не исправлены осознанно. Перед применением нужен подсчёт несовместимых строк; порядок ниже. Такое поведение NOT VALID описано в [документации PostgreSQL](https://www.postgresql.org/docs/current/sql-altertable.html).
- RPC `reschedule_task_secure(uuid,timestamptz,timestamptz,timestamptz,timestamptz)` блокирует задачу, проверяет `auth.uid()`, членство именно в её проекте и завершённость проекта. После блокировки проекта членство проверяется повторно. Право соответствует существующей RLS: автор проекта или участник с принятым откликом; роль исполнителя не вводится как новое ограничение.
- RPC сравнивает обе прежние даты с ожидаемыми через NULL-безопасное сравнение. Устаревший запрос получает `PT409`, даты и история не меняются. PostgREST использует пользовательские коды `PTxxx` для соответствующего HTTP-статуса; здесь это 409 ([документация](https://docs.postgrest.org/en/stable/references/errors.html)).
- Единственный существующий AFTER-триггер `trusted_activity_from_task` при фактическом изменении дат добавляет отдельное событие `task_schedule_changed`. Автор берётся из `auth.uid()`; metadata содержит `task_id`, `task_title`, `old_start_at`, `new_start_at`, `old_due_at`, `new_due_at`. Изменение дат и запись события атомарны. Повтор без изменения дат не создаёт событие. Одновременная смена статуса и дат создаёт по одному событию каждого вида.
- Внутренняя функция истории допускает новый тип события, но клиентские роли не получают EXECUTE. Владельцы, SECURITY DEFINER, search_path и существующие ACL сохранены; CREATE OR REPLACE сохраняет владельца и права, что дополнительно проверено тестом ([документация PostgreSQL](https://www.postgresql.org/docs/current/sql-createfunction.html)). Для новой RPC PUBLIC/anon закрыты, authenticated разрешён с внутренними проверками.
- Перед изменением трёх существующих функций проверяются единственность перегрузки, владелец `postgres`, SECURITY DEFINER, search_path и хеш известного старого/нового тела. Неожиданное состояние или отсутствие ограничений ER-SEC-001 останавливают транзакцию. Ограничения ожидания блокировки/оператора — 5/60 секунд. Есть уведомление PostgREST о перечитывании схемы.

**Совместимость опубликованного сайта.** Прямой UPDATE `tasks` остаётся разрешённым по прежней RLS, но новые правила дат и история работают и для него. Старые клиенты с безусловным UPDATE по id по-прежнему могут перезаписать изменение другого клиента: закрыть такой путь без изменения их контракта нельзя. Новый Гант использует RPC с ожидаемыми датами; обычная форма нового интерфейса использует один условный UPDATE с прежними значениями всех перезаписываемых полей. Проверки конфликтов не означают наличие полного журнала версий/`updated_at` и не обнаруживают последовательность «изменили и вернули ровно прежнее значение».

**Время.** Сохраняются `timestamptz` и фактические моменты времени. Отображение и ввод — в часовом поясе браузера/устройства, как в существующей рабочей зоне; поле часового пояса профиля не переключает календарь. Перенос на сутки сохраняет местное время через календарные дни. Неизменённый ввод формы сохраняет исходные секунды/доли секунды, несмотря на минутную точность `datetime-local`. Специальные случаи пропущенного/двойного часа при DST требуют отдельной браузерной проверки; автоматическое изменение этой семантики не вводилось.

F-02 исправлен **в локальном коде для будущих событий**. Старые пропущенные события не выдумываются и не восстанавливаются. Это подготовка источников ER-005, а не реализация аналитики.

При конфликте данные перечитываются, чужая правка не перезаписывается; при отказе сервера временное перемещение отменяется. Доска, карточка, Гант и месячный календарь проверены на одинаковые сохранённые даты/статусы после перезагрузки. Для задач без дат ничего не выдумывается. ## 6. Непроверенное и ограничения

- **Реальный Supabase: ни один новый сценарий не запускался.** Фактические схема/версии/drift/даты в основной базе неизвестны. Применение ER-SEC-001 и его проверки остаются сведениями владельца из [прежнего отчёта](ER-SEC-001.md), а не новым облачным результатом агента.
- Реальные Auth/письма, Storage, Realtime, Edge Functions и интеграция PostgREST с RPC не подтверждены этими моками/PGlite. Не проверено автоматическое обновление второй вкладки через Realtime.
- PGlite воспроизводит устаревшее последовательное сохранение. Многосессионные гонки настоящего PostgreSQL, ожидания/взаимоблокировки и одновременный отзыв членства/закрытие проекта требуют отдельной репетиции. Нагрузочная ёмкость 5 000/10 000 MAU и сотни задач в Ганте этим заданием не подтверждаются.
- Не выполнены сценарии из непроверенного `project-activity-db.mjs`, полный аудит необычного наследования/настроек ролей ER-SEC-001, специальные DST-часы, Safari/iOS/Firefox и проверка скринридером. Эмуляция touch в Chromium не равна испытанию реального телефона.
- Сохранены ограничения Клода: кнопка чата перекрывает нижний правый угол на 360 px; автопрокрутка доски требует движения указателя; рабочий центр показывает до 6 проектов; названия городов в английском интерфейсе остаются русскими. Тексты `/settings` и `/auctions/[id]` проверены статически, не полным браузерным сценарием.
- Новые отрицательные проверки истории не означают закрытие всех сценариев прежнего ER-SEC-001. Старый body без структурированных статусов остаётся как есть. Исторические пробелы F-02 не заполняются.

3. Если `incompatible_date_order > 0`, **остановить применение и согласовать разбор дат**. Диагностика специально не выводит персональные данные или заголовки. Новая миграция ничего не исправляет; механическое обнуление/перестановка дат недопустимы. Отдельно учитывать, что NOT VALID всё равно проверяет последующие UPDATE этих строк.
4. Проверить прежнюю [диагностику ER-SEC-001](../../supabase/diagnostics/ER-SEC-001-project-activity.sql): все пять служебных функций закрыты для PUBLIC/anon/authenticated. При неожиданной перегрузке, владельце, правах или хеше остановиться и разобрать фактический drift. Не убирать проверки из миграции ради успешного выполнения.

### Шаг 2. Только два новых SQL-файла, в этом порядке

1. Выполнить **целиком** [20261112090000_task_schedule.sql](../../supabase/migrations/20261112090000_task_schedule.sql).
2. После успешного COMMIT выполнить **целиком** [20261112091000_market_system_text.sql](../../supabase/migrations/20261112091000_market_system_text.sql).

Оба файла транзакционные и повторно применяются в локальном тесте без изменения старой истории. Не выполнять baseline заново, не запускать без разбора всю очередь `db push` и не повторять старые миграции автоматически. Если обслуживание миграционной таблицы Supabase делается вручную, запись об этих двух версиях согласовать с используемым владельцем процессом; успешное выполнение SQL Editor само по себе не является проверкой такого учёта.

### Шаг 3. Проверка SQL и совместимости старого сайта

1. Повторить оба read-only диагностических файла. Ожидается новая RPC с владельцем `postgres`, SECURITY DEFINER, `search_path=public, pg_temp`, authenticated EXECUTE=true, anon/PUBLIC=false. У пяти внутренних функций истории PUBLIC/anon/authenticated по-прежнему false; postgres/service_role сверяются старой диагностикой. Права прочих функций не должны неожиданно измениться.
2. Должен остаться один действующий триггер `trusted_activity_from_task` на задачах. CHECK `tasks_schedule_order_check` существует; `convalidated=false` после этой миграции ожидаемо. При нуле несовместимых строк владелец может **отдельно**, в согласованное окно, выполнить `ALTER TABLE public.tasks VALIDATE CONSTRAINT tasks_schedule_order_check;` — это не выполненная агентом операция и не скрытый шаг миграции.
3. На специально выбранном проверочном проекте текущего сайта создать/завершить задачу и изменить её даты штатной формой. Убедиться, что существующие операции работают, история сохраняется и изменение дат даёт одно событие. Не менять посторонние рабочие записи ради проверки.
4. При ошибке остановиться до публикации нового интерфейса. Если RPC пока не видна PostgREST, сначала проверить успешность COMMIT и обновления schema cache; не выдавать внутренним функциям EXECUTE как способ исправления.

### Шаг 4. Публикация кода после проверки SQL

1. Проверить итоговый HEAD `integration/ui-server` и diff относительно фактически актуального удалённого main после его отдельного получения. В этой работе fetch/main merge/push не выполнялись; устаревший локальный main не использовать как источник актуальности.
2. Публиковать согласованную ветку с сохранением её истории: `25bb060`, отдельный `dfe211b`, пять коммитов Клода, merge `fbc0e49`, серверный `e8a89f7` и следующий коммит этого отчёта/состояния. Удобный объект публикации — итоговая ветка, а не набор выборочных cherry-pick. Один пакет Клода без серверных изменений не считать завершённым результатом.
3. После отдельного разрешения на push/merge/deploy — обычная проверка PR, слияние с актуальной основной веткой и production-сборка с действующими настройками. Не публиковать локальную тестовую `.next` и не переносить test-only `NODE_OPTIONS`/фиктивные ключи в production. Рекламные места оставить выключенными по умолчанию. DNS, включая MX/SPF/DKIM/DMARC Яндекс 360, для этой публикации менять не требуется.

### Шаг 5. Приёмка сайта и наблюдение

На согласованных проверочных аккаунтах владельца, принятого участника и постороннего: вход; навигация на desktop/mobile; сохранение статуса с доски и кнопкой; Гант мышью/клавиатурой; редактирование карточки; совпадение статусов/дат с месячным календарём после reload; задачи с одной/двумя пустыми датами. Для двух вкладок открыть одну задачу, сохранить разные сроки по очереди: второе устаревшее сохранение должно показать конфликт и актуальные даты. При отказе сервера не должно оставаться ложного перемещения.

Проверить запрет доступа постороннему/исключённому участнику и изменений завершённого проекта, запрет неправильного порядка дат, одно событие переноса с правильным автором и прежними/новыми датами, отсутствие события при неизменных датах. Проверить реальные Auth, Realtime и скачивание ранее сохранённых обычных файлов и `nearby-pack-v1` с декодером. Полноценную сетевую и многосессионную репетицию выполнять отдельно от произвольных экспериментов в основной базе; результаты зафиксировать, не считать её уже пройденной.

### При ошибке

- Ошибка SQL до COMMIT: откатить открытую неуспешную транзакцию (`ROLLBACK`, если редактор оставил её открытой), сохранить текст ошибки и безопасные метаданные, остановиться. Lock timeout/неизвестный хеш — повод разобрать причину, не снять ограничения.
- Если второй файл не применился, первый остаётся отдельной завершённой транзакцией, совместимой со старым интерфейсом. Не публиковать новый комплект до выяснения причины; второй файл можно повторить после исправления причины.
- Если проблема обнаружена после публикации интерфейса, вернуть известный рабочий frontend **с декодером пакетов**. Аддитивные SQL-изменения можно оставить для совместимости старого сайта. Не удалять новую историю, не открывать внутренний EXECUTE, не заливать старую БД поверх новых пользовательских данных. Серверное исправление/откат готовить отдельно, исходя из фактической схемы и новых данных.
