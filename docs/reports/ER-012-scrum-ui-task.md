## Что сделать в интерфейсе

1. Приватные настройки проекта: simple/kanban/scrum/custom, цель, Definition of Done, этапы/правила, soft/strict WIP, явное делегирование. Существующий проект без строки настроек остаётся simple, версия 0, soft, делегирование выключено. Не менять существующие сценарии доски, Ганта, календаря и файлов. Для Scrum — отдельная панель и переключение «Бэклог / Спринты», а не новый независимый список задач.
2. Оценки доступны в любом режиме: Story Points и плановые часы отдельными полями. NULL — «Не оценено». Баллы: 1/2/3/5/8/13/21; часы >0, <=2000, максимум две десятичные цифры. Фактические часы из `contributions`, не новое поле. Нельзя переводить баллы в часы или рейтинг человека.
3. Бэклог: серверный порядок, операции выше/ниже и клавиатура; если добавляется drag-and-drop, только для порядка бэклога. Не добавлять сортировку внутри колонок, перестановку блоков сайта и перенос зависимых задач. Сохранять полный список UUID с ожидаемой версией, максимум 5000. Большой список не обрезать молча; масштабирование сверх этой границы требует отдельного решения.
4. Спринт: создание/изменение названия, цели и дат; включение/исключение существующих задач; один активный спринт; явный старт со свежими версиями. Planned допускает пустые даты, но если обе заданы — конец позже начала; для старта нужны обе даты и непустой состав. Плановые даты не запускают спринт автоматически.
5. Завершение/отмена: обязательное явное решение ровно для каждой незавершённой задачи — бэклог либо конкретный planned-спринт того же проекта. При отмене обязательна причина. Сначала показать проверяемый итог, затем отправить одну атомарную операцию. Не дублировать задачи и не менять их статусы автоматически. Закрытые спринты — только чтение.
6. Представление истории состава и результатов: стартовый и итоговый снимки, исключённые/удалённые/перенесённые задачи. Для будущего графика использовать реальные снимки и события, отдельно баллы и часы, показывать неоценённые задачи и изменения состава. Не восстанавливать прошлое из сегодняшних tasks, не смешивать отменённые спринты с выполненными. Допустим отдельный последующий этап графиков с честной отметкой отсутствия UI; серверные данные для него уже есть. Это не реализация аналитики ER-005.

## Права и чтение

Чтение новых таблиц разрешено автору и действующим принятым участникам через RLS: `project_planning`, `project_roles`, `project_stages`, `project_backlogs`, `project_sprints`, `project_sprint_items`, `project_sprint_events`. Публичный listing не должен получать приватные цели/правила/состав. Гость, посторонний и исключённый участник доступа не имеют.

| Действие | Кто |
| --- | --- |
| Настройки, этапы, спринты, старт/закрытие, активный состав | Автор; действующий PO/SM только при `delegate_to_roles=true` |
| Назначение ролей и изменение самого делегирования | Только автор |
| Оценки/этап задачи; состав planned-спринта | Действующий участник |
| Порядок бэклога | Автор или действующий Product Owner, независимо от делегирования |
| Удаление задачи активного спринта | Управляющий; сервер дополнительно проверяет даже старый DELETE |
| Любые изменения закрытого проекта | Запрещены |

Назначения PO/SM единственны на проект. Отозванное членство лишает полномочий независимо от сохранённых на экране ролей. UI скрывает недоступные действия, но сервер остаётся источником прав. Не запрашивать service_role и не открывать внутренние функции истории.

## Фактический API

Передавать **именованные аргументы** `supabase.rpc`. Все новые поля настроек и редактируемые поля спринта передаются целиком, а не частичным patch. Типы и безопасный разбор ответа добавить в общий клиентский модуль; не разбрасывать unchecked casts по компонентам. Фактический формат PostgREST отдельно проверить в согласованной среде, не выдавать мок за эту проверку.

| RPC | Именованные аргументы | Результат |
| --- | --- | --- |
| `update_project_planning` | `p_project_id, p_expected_version, p_mode, p_goal, p_definition_of_done, p_wip_mode, p_delegate_to_roles` | Строка `project_planning` |
| `set_project_role` | `p_project_id, p_expected_version, p_user_id, p_role, p_assigned` | Строка настроек с новой версией |
| `upsert_project_stage` | `p_project_id, p_expected_planning_version, p_stage_id, p_expected_version, p_name, p_position, p_category, p_status_value, p_policy, p_wip_limit` | Строка этапа; создание: ID NULL, версия этапа 0 |
| `archive_project_stage` | `p_project_id, p_expected_planning_version, p_stage_id, p_expected_version, p_target_stage_id` | Архивированный этап; занятый требует целевой активный этап |
| `edit_task_planning` | `p_task_id, p_expected_version, p_stage_id, p_story_points, p_planned_hours` | Строка tasks; версия `tasks.planning_version` |
| `get_project_backlog` | `p_project_id` | JSON `{project_id, version, tasks:[полные строки]}` |
| `reorder_project_backlog` | `p_project_id, p_expected_version, p_task_ids` | Тот же JSON; полный порядок UUID |
| `create_project_sprint` | `p_project_id, p_expected_planning_version, p_name, p_goal, p_start_at, p_end_at` | Строка спринта; увеличивает версию настроек |
| `update_project_sprint` | `p_sprint_id, p_expected_version, p_name, p_goal, p_start_at, p_end_at` | Строка planned/active спринта |
| `add_tasks_to_sprint` | `p_sprint_id, p_expected_version, p_tasks` | Строка спринта; `p_tasks=[{task_id,expected_version}]`, <=5000 |
| `remove_task_from_sprint` | `p_sprint_id, p_expected_version, p_task_id, p_expected_task_version` | Строка спринта; задача остаётся |
| `start_project_sprint` | `p_sprint_id, p_expected_version` | Строка спринта со `start_snapshot` |
| `close_project_sprint` | `p_sprint_id, p_expected_version, p_cancel, p_reason, p_decisions` | Строка с `final_snapshot`; решения ниже |

Версия спринта — `project_sprints.version`, бэклога — ответ `get_project_backlog.version`. Любая действительная правка задачи открытого состава увеличивает версию спринта, в том числе через старый интерфейс. Бэклог тоже меняет версию при правках задач/состава. После upsert/archive этапа перечитать версию настроек. Активные позиции и эффективные статусы этапов уникальны; перестановку позиций нельзя отправлять как произвольный массовый UPDATE.

Примеры элементов `p_decisions`:

```json
{"task_id":"UUID_TASK","destination":"backlog"}
```

```json
{"task_id":"UUID_TASK","destination":"sprint","sprint_id":"UUID_PLANNED","expected_sprint_version":4}
```

Не передавать решения для done, удалённых или уже исключённых задач. Сервер отклоняет лишние, отсутствующие и повторные решения. Отменить planned можно и после выхода из scrum, чтобы вернуть оставшиеся задачи. Для обычного завершения нужен active. Нельзя закрыть проект или выйти из scrum при активном спринте.

## Совместимость, история и конфликты

- Единый признак завершения — `status='done'`. Категория done соответствует только этому статусу; другие категории не могут завершать задачу. Старые неизвестные статусы не переименовываются. Эффективный статус этапа — `coalesce(status_value,category)`; не подменять это предположением «любая колонка справа завершена». `completed_at` назначает сервер.
- Строгий режим в API называется **`strict`**, не `hard`. В simple WIP не действует. В soft превышение разрешено и отображается по текущему числу незавершённых задач этапа и `wip_limit`; сервер не возвращает отдельного флага превышения. Policy/DoD — текст, не исполняемые правила.
- Для изменения этапа/оценок использовать `edit_task_planning` со свежей версией и всеми тремя значениями. Для дат сохранить `reschedule_task_secure(p_task_id,p_expected_start_at,p_expected_due_at,p_new_start_at,p_new_due_at)`, время суток и принятую семантику зон. Не переписывать даты при переключении режима.
- Realtime для новых таблиц **не включён**. Перечитывать данные после операции и при конфликте; не заявлять синхронизацию других вкладок без реализованного механизма. На смене аккаунта/проекта отменять действие старых ответов по образцу исправления панели; не переносить ошибки и выбор между пользователями.
- `PT409`: перечитать состояние и предложить явный повтор после согласования. `42501`: убрать недоступные действия/данные. `23514`: объяснить нарушенное правило; `23505`: занята роль/позиция/статус; старый закрытый проект может вернуть `P0001`. Не превращать сетевую ошибку в успешное сохранение.
- Setter с текущей версией и теми же значениями — no-op. Старая версия всегда конфликтует. Реестра request_id нет: после таймаута сначала перечитать, создание/закрытие автоматически не повторять. Закрытие с текущей версией уже закрытого спринта тоже запрещено.
- Историю создаёт сервер атомарно. Не вызывать `append_project_activity_internal`/`planning_*_internal` из клиента и не создавать параллельные клиентские события. Новые типы и metadata описаны в SQL/ER-012; неизвестные старые значения показывать безопасным текстом, без изменения сохранённой истории.
- Итоги читать из `start_snapshot`/`final_snapshot`, детали состава — из `project_sprint_items`; `task_id` переживает удаление, `live_task_id` может стать NULL. События `project_sprint_events` упорядочивать по `id`, пропуски после отката допустимы. Суммы NULL при отсутствии оценок, рядом отдельные счётчики неоценённого; points/hours не объединять.

Сохранение проверить после перезагрузки, согласованно в доске/Ганте/карточке/календаре. Клавиатура, 360 px, фокус, Escape и reduced motion обязательны.
